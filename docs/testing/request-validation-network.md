# 旧版模型请求前校验：网络故障排查

> 本文保留用于排查旧版本与历史诊断包。新版已取消独立前置校验：正式模型请求在 API 内完成额度准入；后台续约和结束同步失败不阻止答案完成。新版应按 [模型日额度验收中的校园网排查](model-daily-token-limits.md#校园网和额度接口故障) 检查实际模型路径。必须先部署新 API，再发布新客户端。

适用于 `ModelDailyQuotaRequestError`、`model_daily_quota_unavailable`，且请求地址以 `/api/usage/token/model-daily/turn` 结尾的错误。

## 已知案例与判断边界

2026-10-28 的诊断包 `ZEN-20261028-095452-D0BADC` 记录了约 10 秒后的 `TimeoutError: signal timed out`。用户保留同一对话、同一模型，切换手机热点后恢复。这个对照把排查重点指向原网络到服务的访问链路；具体是 DNS、IPv6、代理、路由或网络过滤，仍需逐项确认。

未配置模型日限额的密钥也会调用该接口。错误码表示这次校验没有正常完成，不代表日额度耗尽。只有明确的 `model_daily_token_limit_exceeded` 响应才按额度耗尽处理。

## 用户当场恢复

1. 记录失败时间和网络类型，导出失败轮的诊断包。
2. 保留原对话、模型和密钥，重试一次。
3. 仍失败时切换手机热点或其他网络，再重试同一轮。记录切换前后结果。
4. 若换网恢复，继续使用可用网络，再排查原网络；不需要清空对话、调整模型日额度或等待零点。
5. 不关闭证书校验，不在没有服务端授权的情况下绕过额度校验。

## 控制变量：切回原网络，以及 Claude 能用的情况

不要只做一次换网。固定同一客户端版本、入口、服务商配置、密钥、模型和对话，依次测试「原网络 → 热点 → 原网络」，每个网络重试 2—3 次并记录时间。原网络连续失败、热点连续成功、切回原网络又失败，比单次切换更能排除服务恰好恢复的巧合。

每次都以新发起的请求为准。之前已完成的回复、已经取得授权的长任务后续调用，不能证明当时重新申请授权也能成功。

如果 Gemini/GPT 失败而 Claude 成功，先填下面的对照，不能直接按模型名称判断网络可用性：

| 对照项 | Gemini/GPT 失败请求 | Claude 成功请求 |
| --- | --- | --- |
| 入口 | AI 对话 / 新版助手 / 其他 | 记录实际入口 |
| 服务商配置 | 记录配置名称、类型与 ID | 是否完全相同 |
| 实际校验地址 | 诊断包 requestUrl 或 Network 中的 URL | 是否真的发起同一校验接口 |
| 密钥 | 使用后台密钥 ID 或已有指纹，不粘贴原文 | 是否同一把 |
| 新请求时间与结果 | 记录 HTTP 状态或超时、耗时 | 记录校验与生成各自结果 |

普通 AI 对话的校验条件是 `baseProvider.type === 'new-api'` 或地址属于 Zen 托管域名；满足条件时，Gemini、GPT 和 Claude 都在正式模型调用前走同一套校验逻辑。只切换 Anthropic/OpenAI/Gemini 协议并不会跳过这一步。新版助手的转发层是否创建额度授权实例，则还取决于调用时是否传入 dailyModel。

因此：

- 不同入口、服务商或密钥：Claude 成功不能作为失败配置的校验接口可用证据。先比较实际地址与调用路径。
- 同入口、同服务商、同密钥，Claude 也发出相同校验 POST 且成功：说明校验接口并非持续完全不可达。交替测试各模型，进一步区分间歇连接、不同连接选路，以及入口对请求内容的处理；这些都是待验证假设。
- Claude 没有发出校验 POST：核对执行分支、是否为已授权任务、是否出现旧接口 404/405 兼容回退，不能把模型生成成功等同于校验 POST 成功。

不要通过浏览器直接打开 `/turn` 来判断接口可用；实际接口要求带鉴权和 JSON 请求体的 POST，GET 返回 404/405 不能说明实际请求成功。优先在应用里复现并观察真实请求，以便由应用管理授权凭证和释放预留。

## 第一步：在故障电脑比较两条网络

在原网络和手机热点各执行一次。以下命令适用于 macOS 终端，不发送密钥或对话内容：

```sh
curl -sS --connect-timeout 5 --max-time 12 -o /dev/null \
  -w 'http=%{http_code} remote=%{remote_ip} dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} first=%{time_starttransfer} total=%{time_total}\n' \
  'https://zenai.925636.xyz/api/status'
```

- 原网络超时、热点正常：排查原网络路径。
- 两边都正常，但软件仍失败：继续检查软件实际发出的校验请求。`/api/status` 成功只证明该次状态查询可用，不代表带鉴权的校验 POST 可用。
- 两边都失败：同时检查服务入口和服务器状态。
- `http=000`：这次 curl 没拿到 HTTP 状态；结合 stderr 的具体错误判断，不将它视为服务器返回的状态码。

这些时间是从请求开始计算的累计时间，不能直接相加。

## 第二步：检查软件里的实际请求

如果客户端允许打开开发者工具，在 Network 中启用保留日志，筛选 `model-daily`，然后重试原对话。记录：

- 请求的域名、路径、方法、开始时间和总耗时。
- 是否先出现 `OPTIONS` 预检，预检是否成功。
- POST 是否真正发出，是否拿到响应头、HTTP 状态和请求编号。
- Timing 中耗时集中在 DNS、连接、TLS、等待首包还是响应读取。
- 错误是超时、DNS、证书、连接失败，还是明确的 HTTP 错误。

在热点下重复相同步骤比较。若只有预检失败，检查原网络或入口对 OPTIONS/CORS 的处理；若有实际 HTTP 状态，按响应内容排查鉴权、限流或后台错误，不再称为“没有收到响应”。分享截图时不要包含 Authorization、密钥或授权凭证；不要直接分享未经脱敏的 HAR。

## 第三步：细分原网络问题

### DNS

```sh
dig +short A zenai.925636.xyz
dig +short AAAA zenai.925636.xyz
scutil --dns
```

比较原网络与热点的结果。如果原网络解析失败或结果异常，请网络管理员核对解析器和域名过滤规则。CDN 在不同网络返回不同 IP 可以是正常现象，单凭 IP 不同不能认定 DNS 错误。

### IPv4 / IPv6

```sh
curl -4 -sS --connect-timeout 5 --max-time 12 -o /dev/null \
  -w 'IPv4 http=%{http_code} remote=%{remote_ip} total=%{time_total}\n' \
  'https://zenai.925636.xyz/api/status'
curl -6 -sS --connect-timeout 5 --max-time 12 -o /dev/null \
  -w 'IPv6 http=%{http_code} remote=%{remote_ip} total=%{time_total}\n' \
  'https://zenai.925636.xyz/api/status'
```

只有在域名存在 AAAA 记录、电脑也具备 IPv6 连接的前提下，原网络 IPv6 持续失败而 IPv4 成功才提示 IPv6 路径异常。先使用可用网络，再让网络管理员修复，不据此永久强制全部客户端走 IPv4。

### 代理和网络过滤

```sh
scutil --proxy
```

核对 Zen AI 的网络设置、系统代理/PAC、VPN，以及公司网络的域名过滤或 HTTPS 检查。终端 curl 与应用未必使用相同代理配置，因此以软件实际请求的对照结果为准。证书错误应检查证书链和受信任配置，不使用 `curl -k` 掩盖问题。

## 第四步：服务端关联

历史案例的时间是北京时间 2026-10-28 09:54:42—09:54:52。Docker 部署可先查看应用访问日志：

```sh
docker logs --timestamps \
  --since '2026-10-28T09:54:35+08:00' \
  --until '2026-10-28T09:55:10+08:00' \
  zen-api 2>&1 | grep -E 'model-daily|model daily quota|TokenAuth'
```

如果容器名称不同，替换 `zen-api`。再次复现时可以改用 `docker logs --timestamps --since 10m zen-api`。应用访问日志通常在请求结束时输出；请求仍在处理时，不一定已经出现完整日志。

同时查看反向代理、CDN或隧道入口的访问日志，按失败时间、路径、方法和用户出口 IP 关联，检查状态、请求耗时和上游响应耗时：

- 入口没有记录：优先检查客户端到入口的解析、连接和 TLS；同时确认该入口确实启用了访问日志。
- 入口有记录，应用没有：检查入口到应用的转发、路由和上游连接；也要排除日志缺失或请求尚未结束。
- 应用有记录且处理很快，客户端仍超时：检查响应返回路径、预检和入口转发。
- 应用处理超过 10 秒：检查 TokenAuth 的密钥/用户查询、Redis 限流以及 `BeginModelDailyTurn` 的数据库事务、连接池与锁等待。
- 收到 401/403/429/5xx：结合响应体区分鉴权、明确额度拒绝、限流和后台错误；不要只按状态码猜原因。

当前额度准入请求没有携带本轮 trace/operation 头，后台详细诊断采集也仅覆盖 `/v1` 路径。因此，旧包中的 traceId 不保证能查到这条 `/api/usage/...` 请求，`zen-api-evidence.json` 无记录也不能证明它没到服务器。这个案例应优先查上述普通访问日志。

## 本次修正与后续可靠性方向

- 客户端把校验超时、连接失败和其他校验异常分别展示，不再统一提示额度服务不可用。
- 界面分类与诊断摘要使用一致文案；连接问题给出换网络和检查代理的恢复步骤。
- 保存校验错误时保留底层 Error/DOMException 的名称和消息，避免原因被序列化成 `{}`，导致重新打开历史后无法识别超时或连接失败。
- 对话时间线记录校验开始、完成或失败以及耗时；旧包只有 context 错误时，也根据原始错误识别校验阶段，不直接归因为本地程序故障。
- 现有授权实现允许同一实例使用相同 task_id 重试失败请求，避免重复预留。本次不新增自动重放；如后续增加自动重试，应最多一次、仅针对确认可重试的连接故障、保留同一 task_id 并尊重用户取消。明确额度拒绝、鉴权失败和证书错误不自动重试。
- 后续可把校验请求纳入端到端关联和只读网络检测；备用入口必须由产品明确配置并使用受信任 HTTPS 地址。不能以任意域名替换或静默切换模型来处理网络故障。
