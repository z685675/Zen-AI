## 一、开始前准备

1. 先更新服务器上的 Zen API，再安装 GitHub 根据 v1.1.74 标签生成的 Zen AI 安装包。不要拿旧安装包或 pnpm dev 的结果替代安装包测试。
2. 备份软件数据和 API 设置。只用脱敏资料，在自己的“Zen AI 手测”新文件夹操作，不动真实办公原件。
3. 不同时启动共用数据的开发版和安装版。打开关于页面确认版本为 1.1.74。
4. 选择四个实际可用的文字模型，每家一个。下面填完整 ID，后文不再硬编码容易变化的型号：

| 厂商 | 本次完整模型 ID | AI 对话 | 新版助手 |
| --- | --- | --- | --- |
| GPT | 待填 | 待测 | 待测 |
| Gemini | 待填 | 待测 | 待测 |
| Claude | 待填 | 待测 | 待测 |
| Grok | 待填 | 待测 | 待测 |

5. 使用专用测试 Key，不把 Key、Cookie、客户资料写进测试结果。真实问答、图片、自动探活可能收费；先用低价模型做大部分功能，四家各补兼容检查。
6. 同一张表的结果记录“通过／失败／待测／不适用（说明原因）”，未测不能算通过。
7. 涉及停用渠道、远端策略、账户额度、恢复探活的测试，只在隔离环境和测试分组进行。不要为了验收停掉生产所有用户的模型。
8. Windows 和 macOS ARM 都在发布范围时都要实测。Mac Intel 如同时发布，也需独立抽检；没有机器时标“待测”，不能拿 Windows 代替。

本次已推送的 API 修复提交为 `02d42bd03`（空流重试与真实错误返回）。服务器应部署包含该提交的最新 main；只更新 Zen AI 不能修复仍运行旧代码的服务器。

### 本轮主要变化

- 大附件、多附件分段读取，办公文件隔离解析及事件接收加固。
- 文件默认另存、同名避让；内置文件工具覆盖原件的确认与备份。
- “我的用量”历史、筛选和趋势。
- 新版微信轻助手、电脑续聊回传、定时任务。
- 有效渠道决定模型可见性；文字备用链、状态同步及稳定恢复回切。
- 流式异常、退出清理，以及 AI 对话大输入整理后保留当前提问的修复。
- 现有自动验收工具一并保存，但本次先不依赖它的真实模型验收结果来签收。

### Q02｜四家模型 × 两个入口，基本回答与追问

每个模型在“AI 对话”和“新版助手”各新建一个会话，逐条发：

~~~text

~~~


预期：测试成功、记住了、海风7319。能连续回答，不出现空白成功、无限转圈或闪退；无需运行脚本来回答“你好”。

记录首个可见内容的等待时间和整轮用时。某家明显比其他家慢时保留该轮证据，不连续重发覆盖现场。

### Q03｜先制作一套能核对的素材

只在新版助手用一个可靠低价模型发：

~~~text
请在一个新的“手工验收7319”文件夹里，制作下面六个真实文件，不要覆盖任何已有文件，不联网、不安装软件：
共同项目编号 ZX7319，客户叫青禾，负责人林悦，交付日2026年11月20日。
三笔支出是材料120元、制作230元、运输350元，合计700元。
旧预算600元已经作废，最终预算700元。
1. Word：一页项目说明，写清这些信息。
2. Excel：两张工作表，“明细”写三笔支出并用公式计算合计，“说明”写项目编号、负责人和最终预算。
3. PPT：四页，分别是概况、费用、交付计划、最终结论，关键数字直接放在页面上。
4. PDF：两页，中文可读，最后一页明确写最终预算700元。
5. JSON：保存项目编号、负责人、交付日、三笔费用、最终预算，最后一个字段叫test_marker，值是END-7319。
6. TXT：写同样的项目信息。
生成后给我每个文件的打开入口；没有做出的文件明确说出来，不要把纯文字或改扩展名当文件。
~~~

人工先打开全部素材核对：不是空文件；Word、PPT、PDF 没有乱码或严重溢出；Excel 公式合计 700，JSON 可阅读。若素材生成有误，先记“生成失败”，修正素材后才能用于读取测试。

另准备一张自己能看清的 PNG 和一张 JPG：可对刚才的项目说明截图，确保含 ZX7319、700、林悦。保留原图作为答案，不需要特殊制图工具。

### Q04｜两入口读取办公文件，Mac 必测

预期：ZX7319、林悦、2026-11-20、120/230/350、合计700，600作废；不能遗漏文件却说全部看完。Mac ARM 重点观察 Excel 发送后是否卡顿、闪退。


### M05｜大附件、多附件、损坏和取消

准备真实脱敏材料，不靠改扩展名模拟正常文件：

1. 新版助手上传一份约10MB或更大的原先失败 PDF。
2. 同轮上传 PDF、Word、Excel、PPT，总大小超过10MB；记录每份文件大小。
3. 上传较大 PNG/JPG；如图中文字很小，另给局部清晰图核对。
4. 上传较长单行 JSON，末尾有容易核对的标记。
5. 多附件里混入一份专门准备的损坏副本。
6. 读取中点击停止，随后要求只继续未完成部分。

~~~text
请先列出我上传的全部材料，再逐份说明主要内容，最后比较目标、预算、日期和矛盾。注明来源。没读完、损坏、看不清或超限的文件分别说清楚，不要用猜测补齐。
~~~

继续提示：

~~~text
继续处理刚才还没完成的材料，不要重新生成已经完成的文件，也不要改动原件。
~~~

通过：不闪退、不因合法大事件无故中断；支持分段/按需阅读；遗漏和失败说清；停止后能继续；不重复提交已有文件操作。

当前新版助手文档读取保护参考：普通文档单份64MiB、文本256MiB，Office还有解包/结构上限。这不是保证任意大小、任意复杂文件都能全读。图片会缩放，细小文字可能受影响。界面/平台如有更小上传限制，以实际提示为准；超限应明确拒绝，不能静默丢掉。不要为了快测试构造压缩炸弹。

### M06｜文件安全和 Python 实际处理

所有操作只在专用测试文件夹，重要目录和原件不授权。

1. 用 Q05 的另存修改检查原件700、新版750均保留。
2. 再说“再生成一份同名文件，内容写第二版”，应换名或编号，不静默覆盖。
3. 新建一份可丢弃的说明.txt，内容“第一版”，明确让助手覆盖。先拒绝，再重新发指令并同意。
4. 检查内置覆盖流程：准确路径、取消默认、备份仍是第一版、原件变第二版。计划模式不能真的创建/修改文件。
5. 删除一份专门的待删除.txt，确认范围独立，不顺手清理目录或备份；关闭确认不执行。
6. 全自动模式也抽检内置覆盖确认，不能因为模式不同就跳过备份保护。

覆盖提示词：

~~~text
请覆盖这个测试文件：[粘贴说明.txt的准确路径]，内容改为“第二版”。这是覆盖原件，请先让我确认，并保留第一版备份。不要修改其他文件。
~~~

验证 Python：

~~~text
请用本地Python数据处理工具读取这份Excel，检查每项费用并计算合计，画一张费用对比图，另存图片给我。不要安装软件，不改原表。请说明你是否实际执行了工具；如果环境没准备好就直说。
~~~

只有实际工具执行并产出图片，才算 Python 能力已验证；普通心算/文件生成成功不能替代。应使用 Zen AI 私有运行时，不要求用户手动改系统 Python。

安全边界：这不是操作系统沙箱。任意终端、Python脚本或第三方MCP不保证都被内置文件工具的覆盖备份机制拦住。不要为不可信技能授权重要目录或全自动；不能因上述测试通过就承诺任意脚本绝对安全。

### M09｜远端策略、故障备用、自动回切

在测试分组准备 A/B/C，另备 D 作手选偏好。默认A，备用B、C，名单/Key权限均正确。发布策略与只保存草稿区分开。

| 步骤 | 操作 | 应有表现 |
| --- | --- | --- |
| 1 | A有两条有效渠道，仅停一条 | A保留；高优先级坏而低优先级可用也保留 |
| 2 | 禁用A全部渠道，含路由成员与渠道列表状态 | A隐藏，受影响的空闲选择用B |
| 3 | B也全部失效 | 继续C，不绕到其他Provider/未配置贵模型 |
| 4 | 所有候选失效 | 留空并保留草稿、历史和原偏好，阻止无效新请求 |
| 5 | 自动禁用的A第一次探活成功 | 不立即启用；约每分钟复测，首次加后续3次成功，跨度至少3分钟 |
| 6 | API恢复A，B正常 | A重新可见；客户端再观察至少5分钟，在空闲时回A |
| 7 | 观察中A又坏 | 重新观察；反复波动会延长客户端等待 |
| 8 | A已恢复可用，B也失效 | 下一次选择优先尝试A，不机械跳C |
| 9 | 用户主动改选D，或明确选B为新偏好 | 不因旧A恢复强制拉回 |
| 10 | 手动停用渠道 | 自动探活不能擅自打开手动停用 |
| 11 | 请求正在正常输出时状态变化 | 不打断、不重放；后续一轮才换 |
| 12 | 断网/401/代理错误页面 | 不把失败响应当有效空列表清光模型 |

从API首次探活成功完成到正常回切，理想情况下至少约8分钟，还要加探测、同步和等待空闲；不是从上游恢复那一秒精确计时。需开启后台定期测试、成功后重启用、渠道允许自动探活等适用开关。手动点启用不能算自动恢复测试。

补测对话、快速、翻译、命名、新助手、微信、定时的受影响模型；不只看主对话。备用必须满足用途和权限，不以图片/音频/向量代替文字模型。

实时通知断开后，有重连及约5分钟轮询兜底；不承诺所有网络状态下立即生效。受管Provider按现有域名规则生效，第三方同名模型应独立。不要用无关本地地址的结果直接判断线上受管策略全部正常。

## 四、怎么判定可以发版

- 必须没有：闪退、重要原件损坏、越权访问/外发、重复执行有副作用任务、普通请求普遍不能回答、空回答假成功、串Key/微信账号。
- Q01～Q09有明确结果；本轮发布的微信、定时、模型联动不能全部标未测。
- M项按实际发布范围补齐，未完成的平台/格式/压缩证据标待测；必要时缩小或关闭相关发布能力，不能把未测改成通过。
- 单个渠道的真实故障与客户端缺陷分别记录；不能靠连续重试一次成功抹掉最初问题。
- 先对候选安装包手测，修复后只重测关联部分和必要基本链路；不要求每个小改动都四家全格式全量重跑。
- 任何影响流式返回、工具执行、权限、数据库/升级、默认模型或全局渠道的修复，应补两入口核心问答及相关关键回归。
- 最后还原测试渠道/策略、暂停周期任务、断开不需保留的微信连接，检查没有持续付费测试。
- GitHub打包成功只表示构建产物生成；最终公开发布由你在人工验收后决定。
