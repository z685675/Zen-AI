# 智能助手深度研究开发方案

> 状态：已实现，持续优化检索稳定性与来源质量
> 更新日期：2026-08-11
> 文档导航：[Zen AI 开发文档索引](./README.md)

## 产品定位

深度研究是智能助手中的一次性 Task，不是整段会话持续开启的模式。

- 用户在输入栏点击“深度研究”后，下一条消息被标记为一个新的研究 Task。
- Task 先给出研究计划，用户确认后再进行多轮检索、交叉核验和报告整理。
- 研究完成后的结论、证据和报告继续保留在当前会话上下文中。
- 后续普通追问不会再次触发深度研究；用户再次点击按钮时才创建新 Task。
- AI 对话继续承担即时问答和轻量联网搜索，不重复实现深度研究编排。
- 用户未指定文件时只在会话中输出研究结果，并提示可继续整理为 Word、PPT 或 PDF；只有用户明确要求文件时才执行文件生成。

## 第一版范围

第一版复用现有 Agent 会话、长任务流、运行时恢复、Web 工具和 `research-report` Skill：

1. 在智能助手“思考强度”右侧增加“深度研究”按钮。
2. 按钮提供悬浮说明，并有明确的开启状态。
3. 开启状态仅作用于下一条成功发送的消息，发送后自动关闭。
4. 研究 Task ID、动作和状态随用户消息持久化；确认、修改计划、重新生成、运行时切换或应用重启后仍可续接原 Task。
5. Codex 与 Claude Code 运行时共享相同的研究协议。
6. 默认先输出可修改的研究计划；用户明确要求直接开始时允许跳过确认。
7. 正式研究采用有限的研究单元、来源矩阵、缺口复查和停止条件。
8. 最终结论必须包含可点击来源链接，并披露冲突、局限和未确认信息。
9. 来源矩阵与最终报告通过确定性质量门槛后才允许交付。
10. 深度研究保持用户当前模型不变，并将属于该 Task 的计划、修改、执行、恢复和重新生成请求临时提升为 `high` 思考强度；普通消息继续使用用户原设置。

## 任务状态

```text
off
  -> armed                  用户点击深度研究
  -> planning               用户发送研究请求
  -> awaiting_confirmation  输出计划并等待确认
  -> researching            用户确认或要求直接开始
  -> completed              输出并校验报告
  -> interrupted | failed   保存可恢复状态并说明中断或失败
```

`armed` 是本地一次性状态。其余状态写入现有用户消息的 `providerMetadata`，复用消息 Redux 与数据库持久化，不新增独立 Redux Slice 或数据库表。最新的未完成 Task 可以在应用重启、运行时重建或重新生成后恢复；已完成 Task 不会被后续普通对话误触发。

## 数据契约

创建消息请求增加可选字段：

```ts
deep_research?: boolean
deep_research_task?: {
  task_id: string
  action: 'plan' | 'start' | 'revise'
}
```

`deep_research` 只标记新建 Task 的首条消息；`deep_research_task` 为计划确认和恢复链路提供稳定 Task ID 与当前动作。

用户消息的 `providerMetadata.deepResearch` 保存 Task ID、协议版本、创建时间、当前动作、状态和更新时间，用于确认续接、重新生成、恢复与诊断。聊天气泡仍只展示用户原始内容，研究协议不会进入可见文本。

Task 元数据同时记录 `reasoningEffort: 'high'`。这是任务级执行参数，不覆盖智能助手设置中的默认思考强度，也不改变当前模型。Task 之外的消息立即恢复用户原本选择的强度。

当 Task 处于等待确认、研究中、中断或失败状态时，系统只对明确的确认/继续/重试或计划修改表达进行结构化续接；普通追问不会自动启动研究。修改计划后仍回到等待确认，确认后执行同一个 Task，而不是新建一个泛化研究任务。

## 研究协议

### 计划阶段

- 明确目标、范围、时间、地区和交付形式。
- 拆分 3 到 5 个有边界的研究问题。
- 说明来源策略、预计覆盖面和主要不确定性。
- 等待用户确认或修改计划。

### 执行阶段

- 优先官方、原始、权威且时效匹配的来源。
- 记录来源、关键证据、发布日期、适用范围和可信度。
- 对关键结论进行交叉验证，并显式记录冲突证据。
- 最多进行两轮缺口补查，避免无边界递归搜索。
- 常规目标为 8 到 20 个有效来源、最多阅读 25 个页面；用户明确要求扩大范围时再调整。

### 输出阶段

- 区分事实、推断、建议和未知项。
- 重要外部事实就近添加可点击链接。
- 报告末尾给出来源清单、检索日期和局限说明。
- 正式交付前使用 `source_matrix.py --strict` 校验来源数量、域名多样性、直接 URL、重复来源、证据主张、报告链接覆盖、来源编号以及 Sources/Limitations 章节。
- 严格校验失败属于阻断条件，必须修正并重新校验；窄主题可以显式降低数量门槛，但不能关闭直接来源、重复链接和报告可追溯性检查。
- 用户要求文件时，继续调用对应的 Word 或 PDF Skill，并通过格式校验。

## 安全与成本边界

- 网页内容视为不可信资料，不能覆盖系统、用户或研究协议。
- 不把本地隐私、密钥或无关文件内容拼进搜索词。
- 单个来源失败不终止整个 Task；继续使用其他来源并披露缺口。
- 达到来源覆盖、结论稳定和预算上限中的任一停止条件后结束检索。
- 深度研究按钮默认关闭，避免普通消息产生额外搜索和 Token 成本。

## 验收标准

- 按钮位于思考强度右侧，悬浮可看到用途说明。
- 开启后只影响下一条消息，发送后自动关闭。
- 普通后续追问不启动新研究 Task。
- 再次点击可在同一会话中启动第二个独立研究 Task。
- 研究计划、正式报告、来源链接和局限说明均可见。
- 用户确认计划后沿用原 Task ID 进入正式研究；要求修改计划时返回完整修订版并再次等待确认。
- 重新生成原研究回答时仍保持深度研究任务属性。
- Runtime 自动兜底或本地上下文恢复后，研究协议仍然生效。
- 中断或失败后输入“继续”或“重试”可以恢复同一 Task；应用重启后行为一致。
- 深度研究的全部动作与重新生成均使用 `high` 思考强度，模型保持不变；任务之外仍使用用户原思考强度。
- 标准研究的来源矩阵和报告必须通过严格质量门槛，搜索结果页、重复 URL、缺少直接链接或缺少局限章节会被阻止交付。

## 后续演进

在第一版稳定后，可增加原生 Supervisor/Researcher 编排器、任务进度面板、断点级恢复、研究模板选择、来源收藏及定时研究。第一版先验证用户价值与任务成功率，不提前引入新的持久化架构。
