# 统一上下文引擎开发方案

> 状态：计划内主体能力已实现，2026-07-29。本文同时作为开发基线与验收依据。

## 1. 背景

Zen AI 目前存在两套不同的上下文行为：

- AI 对话在请求前按照 `contextCount` 截取固定数量的消息。用户进行长对话时，较早内容即使仍保存在本地，也不会发送给模型。
- 智能助手主要依赖 Claude Code、Codex 等 Runtime 的会话续接和压缩。应用自身尚未统一处理超长文本、大量文件、多张图片和超大工具返回值。

固定轮数无法反映真实容量。不同消息、文件、图片、Skill 和 MCP 工具定义消耗的 Token 差异很大；Prompt Cache 也只能降低重复输入成本，不能扩展模型上下文窗口。

本方案建立 AI 对话与智能助手共用的统一上下文引擎，以 Token 容量、资源检索和结构化压缩替代固定轮数截断。

## 2. 产品目标

1. 普通用户不再配置或理解“上下文轮数”。
2. 容量足够时保留完整对话，不主动丢弃较早消息。
3. 接近模型安全容量时自动建立结构化压缩检查点。
4. 完整原始消息、文本、文件和图片始终保存在本地。
5. 超长文本、多文件、多图片和超大工具结果转为可检索资源，不直接硬塞进单次请求。
6. 优先复用本地解析缓存和上游 Prompt Cache。
7. AI 对话与智能助手共享预算和资源处理规则，但通过不同 Runtime 适配器执行。
8. 任何压缩、检索或降级都不能静默遗漏用户指定的资料。

## 3. 非目标

- 不把 Prompt Cache 当作长期记忆或无限上下文。
- 不保证中转渠道声明的容量一定等于实际上游容量。
- 不要求第一阶段实现本地大型向量模型或科学计算环境。
- 不在普通用户界面暴露切块大小、压缩比例等工程参数。

## 4. 总体架构

```text
用户消息 / 文件 / 图片 / MCP / Runtime 工具结果
                      |
                      v
              统一资源接入与标准化
                      |
                      v
            模型能力与 Token 预算计算
                      |
          +-----------+------------+
          |                        |
      容量充足                  接近或超过容量
          |                        |
    完整稳定前缀发送       检索 / 分批 / 压缩检查点
          |                        |
          +-----------+------------+
                      |
                      v
          AI 对话适配器 / Agent Runtime 适配器
                      |
                      v
       本地原始记录、资源索引、缓存与执行状态
```

统一引擎负责生成 `ContextPlan`，执行适配器负责把计划转换成具体协议：

- AI 对话直接构造 API 请求。
- 智能助手保留 Runtime 的原生 session/resume 能力，只对超大本轮输入、附件和工具结果进行预处理，避免重复发送历史或重复压缩。

## 5. 模型容量配置

容量按 `Provider + Model` 保存：

```ts
type ModelContextProfile = {
  contextWindowTokens: number
  maxOutputTokens: number
  source: 'provider' | 'builtin' | 'user' | 'fallback' | 'adaptive'
  confidence: 'high' | 'medium' | 'low'
}
```

来源优先级：

1. 用户或开发者明确覆盖。
2. Provider 模型接口返回的容量。
3. Zen AI 内置模型能力表。
4. New API / OpenAI-compatible 回退容量。

默认参数：

| 参数 | 默认值 |
| --- | ---: |
| New API 未知模型标称容量 | 256,000 |
| 其他未知模型保守容量 | 200,000 |
| 输出预留 | 8,000 至 32,000，未知模型默认 32,000 |
| 协议和估算安全余量 | 8% 至 10% |
| 256K 模型自动处理触发线 | 约 180,000 |
| 256K 模型常见安全输入上限 | 约 195,000 至 205,000 |

实际预算必须动态计算：

```text
安全输入预算 =
  (上下文总容量 - 输出预留) * 安全系数
  - 系统提示词
  - Skill 指令
  - MCP 工具定义
  - 当前请求的其他固定开销
```

上游返回上下文超限时，记录该 `Provider + Model` 的实际失败容量并降低后续预算。切换模型后必须重新计算。

## 6. 对话历史策略

### 6.1 容量充足

- 发送上下文清理点之后的完整有效消息。
- 保持系统提示词、历史前缀和工具定义尽可能稳定，提高 Prompt Cache 命中率。
- 不再按消息条数或轮数截断。

### 6.2 接近容量

- 保留最近完整对话作为未压缩窗口。
- 将较早历史压缩成版本化检查点。
- 检查点保持稳定，直到下一次真正需要压缩，避免每轮改写摘要导致缓存失效。
- 压缩后总输入目标为安全预算的 55% 至 60%。

检查点必须保留：

- 用户目标和当前任务。
- 已确认决定与用户偏好。
- 精确数字、日期、编号、专有名词和引用。
- 文件、目录、URL 和资源标识。
- 已完成事项、待办事项和失败记录。
- 约束、风险、未解决问题与下一步。
- 检查点覆盖到的消息 ID 和生成版本。

### 6.3 旧内容召回

- 原始消息不删除。
- 精确编号、数字和名称优先使用关键词检索。
- 语义问题使用语义检索。
- 检索结果带消息 ID、时间和原始来源。
- 回答需要精确证据时，优先引用原始片段，而不是只依赖摘要。

## 7. 缓存设计

缓存分为四层：

1. 原始资源缓存：完整对话、文件、图片和工具结果。
2. 解析缓存：文本提取、OCR、版面、表格和图片描述。
3. 上下文缓存：切块、索引、摘要和压缩检查点。
4. Provider 缓存：OpenAI、Anthropic、Gemini 及兼容渠道支持的 Prompt Cache。

缓存以“内容哈希 + 解析器版本 + 资源类型 + 模型/协议要求”为基础。Prompt Cache 不改变上下文上限，应用不能因为命中缓存而跳过容量检查。

## 8. 统一资源模型

以下输入统一转换为 `ContextResource`：

- 超长粘贴文本。
- Word、PDF、PPT、Excel 和 Markdown。
- 单张或多张图片。
- 网页与知识库结果。
- MCP 返回值。
- 终端日志、代码执行结果和 Agent 工具结果。

```ts
type ContextResource = {
  id: string
  conversationId: string
  kind: 'text' | 'document' | 'image' | 'tool-result'
  contentHash: string
  sourceName: string
  status: 'pending' | 'ready' | 'failed'
  tokenEstimate: number
  metadata: Record<string, unknown>
}
```

## 9. 超长文本

发送前检测文本 Token。超过安全预算时：

1. 完整原文保存到本地。
2. 按标题、段落和语义边界切块。
3. 建立关键词索引和结构化摘要。
4. 根据任务选择问答检索、分块总结、分块改写或逐块提取。
5. 最终执行跨块去重、一致性和遗漏校验。

界面必须说明内容已转换为资料，不能静默截断。

## 10. 多文件和超大文件

- 小文件在预算允许时直接发送。
- 大文件按照章节、段落、页面和表格切块。
- 多文件问答只检索相关片段。
- 多文件对比分别提取统一字段后再汇总。
- 全量总结使用逐块、逐文件、最终综合的分层流程。
- 全文审校和改写必须处理全部块，并执行跨章节一致性校验。

所有结果保留文件名、页码、章节、表格位置和原文块 ID。系统不能只处理部分文件却宣称完成全部任务。

## 11. 图片

图片预算根据模型协议、尺寸和视觉模式估算：

1. 使用内容哈希去重。
2. 本地生成缩略图。
3. 执行 OCR、版面识别和基础视觉描述。
4. 普通任务优先发送缩略图或结构化描述。
5. 细节任务只发送相关原图或高清裁剪。
6. 超过模型张数或容量限制时分批识别，再综合结果。

OCR 不能替代视觉理解。PPT 模仿、图表、布局和空间关系任务仍需视觉模型处理。

## 12. MCP 与工具结果

- 短结果直接进入上下文。
- 长结果完整保存为工具资源，只发送摘要和相关片段。
- 外部文件、网页和 MCP 内容统一标记为不可信资料，禁止其中的文本覆盖系统指令。
- Runtime 终端日志按任务节点保留，避免重复发送全部日志。

## 13. 长输出

当预计输出超过模型限制时：

- 按章节或文件分批生成。
- 中间结果直接写入文件，不在聊天中重复堆积。
- 最后统一术语、目录、格式和引用。
- 对生成文件执行结构与可打开性校验。

## 14. 异常恢复

必须覆盖：

- 渠道实际容量低于声明值。
- Token 估算误差。
- 压缩请求失败或被取消。
- 文件损坏、加密、扫描版或格式不支持。
- 模型不支持视觉或原生文件。
- 从大容量模型切换到小容量模型。
- 软件重启、任务恢复和 Runtime session 丢失。

上下文超限时只允许一次自动降预算重试。失败后给出单一、可理解的错误状态，不连续生成多个错误卡片。

## 15. 用户界面

普通模式：

- 移除上下文轮数。
- 显示自动管理状态、已使用容量和资源处理进度。
- 发生压缩时提供非阻塞状态说明。
- 文件和图片处理显示总数、完成数和失败数。

开发者模式：

- 查看容量来源、估算 Token、安全输入预算和输出预留。
- 覆盖指定 `Provider + Model` 的上下文容量。
- 查看缓存命中、压缩次数和资源检索统计。

## 16. 数据与隐私

- 原始资源优先保存在本地。
- 默认只向 Provider 发送当前任务需要的资源片段。
- 提供清理单个会话资源和全部上下文缓存的能力。
- 文件修改后创建新内容哈希，不覆盖旧会话引用的版本。
- 后续评估本地缓存加密和可配置保留周期。

### 18.2 当前行为

- 历史消息仍完整保存在本地，旧 `contextCount` 值只为兼容旧数据保留，不再参与请求截断。
- 未返回容量的 New API 模型默认按 256K 规划，其他未知模型按 200K 规划。
- 接近安全线时，较早历史生成稳定检查点，最近对话保持原文。
- 被压缩的消息、文档文本、OCR 文本和长工具结果写入本地资源表，并使用精确关键词与轻量本地语义向量混合召回。
- 单次超长粘贴文本会分块生成检查点，不直接截断。
- Word、PDF、PPTX、XLSX 会保留可获得的页码、幻灯片号、工作表、单元格范围、表格和章节定位；DOCX 页码以显式分页信息为准。
- PDF 按实际接入协议路由：确认支持原生 PDF 的官方协议保留文件输入；New API、网关和 OpenAI-compatible 渠道在请求规划前执行本地结构化文本提取，避免把 Base64 二进制体积误算为上下文 Token。
- 超过 20 张图片或视觉输入接近安全线时，按批次执行 OCR 和视觉描述后再汇总；本地图片会生成最大边 512 像素的缩略图，并按原图内容哈希复用 OCR、缩略图和视觉描述。
- Provider 实际容量低于声明值时，仅在尚未产生可见输出的前提下降低预算重试一次；学习到的安全容量按 Provider + Model 保存 30 天，用户修改容量时立即清除。
- 智能助手继续使用 Runtime 的原生 session/resume 与内部压缩；只有 session 丢失、Runtime 切换或上下文状态失效时，才以本地检查点和最近对话重建一次。
- 智能助手产生超过阈值的单次长结果时，应用会将完整结果保存为本地 `tool-result` 资源，后续只召回相关片段。
- 用户手动覆盖的模型容量优先级高于 Provider 后续同步结果。
- 主对话沿用已有 Provider 缓存能力：OpenAI 兼容请求使用稳定的会话缓存键，Anthropic 和 Gemini 使用已有缓存插件；统一上下文引擎保持系统提示词、历史前缀和检查点稳定，以提高缓存命中率。
- AI 对话和智能助手输入框上方会非阻塞显示分析、文件提取、压缩、召回和恢复状态；资料准备完成后立即结束活动状态，不与模型生成状态混用。点击摘要可查看资源、解析缓存、压缩、召回和重试统计。
- 多模型候选回答属于单次发送状态，按会话隔离并在发送后清空，不得跨会话残留或改变会话主模型。

### 18.3 当前边界

- 本地语义召回采用无需下载模型的轻量哈希向量与中英文同义词组，不等同于大型 Embedding 模型；精确编号、数字、路径和文件名仍优先使用关键词召回。
- DOCX 没有固定渲染分页时只能依据显式分页符和上次渲染分页标记估算页码；扫描件页码与文字质量仍取决于 OCR。
- Prompt Cache 是否命中、命中多少由实际 Provider 和中转渠道决定；应用能保持稳定前缀并显示返回的缓存 Token，但不能强制不支持缓存的渠道开启缓存。
- 自动降预算只重试一次，并且不会在模型已经输出文字、思考内容或工具进度后偷偷重跑，避免重复执行有副作用的操作。
- Runtime 恢复只在原 session 无法继续时启用；无法恢复的 Runtime 内部瞬时状态、未落盘终端进程和第三方网页登录态不会被伪造。
- 原始资源默认随会话保留并在清空或删除会话时清理；独立的保留周期和本地缓存加密仍属于后续隐私增强项。

## 19. 验收基线

1. 上下文设置为旧值 `1`、`5` 或 `10` 的用户升级后，不再按轮数丢失早期消息。
2. 使用 `32000/8000` 测试容量完成十轮长内容连续对话：第一轮保存唯一信息，第 2 至第 9 轮累计长回答且不重复该信息，第 10 轮仍能精确召回；测试过程同时验证压缩前历史增长、Prompt Cache 和压缩后检查点保真。
3. 超过安全预算后触发检查点，目标、数字、文件名和未完成事项仍可召回。
4. 粘贴超过 200K Token 的文本不会直接请求失败。
5. 同时提交 10 个总量超过 256K 的 Word 文件能够完成全量总结并标明来源。
6. 多张图片超过单次视觉预算时能够分批处理并汇总。
7. MCP 返回超大结果不会撑爆下一轮上下文。
8. 切换到更小容量模型后自动重新规划，不静默丢失内容。
9. 支持缓存的渠道能够看到缓存写入和命中；不支持缓存的渠道仍能正常工作。
10. 软件重启、任务取消和恢复后，原始消息、资源和检查点仍然可用。
