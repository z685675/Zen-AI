# 错误诊断包：链路定位与测试

本次修改不改变模型、底座选择、计费和上下文处理规则。诊断记录为旁路元数据，不保存完整请求/响应正文，不额外调用模型。只有用户点击导出时，才向当前 Provider 的兼容 Zen API 发起只读证据查询。

## 如何查看

1. 用户在 AI 对话或智能助手的报错卡片点击“导出诊断包”。
   单条消息的渲染发生异常、普通报错卡片显示不了时，渲染错误提示也提供导出按钮。
2. 管理员先看 `链路结论.txt`，再看 `collection-manifest.json` 是否有证据缺失。
3. 用 `timeline.json` 查看客户端准备、上下文、底座启动、自动恢复、HTTP 收发、状态更新及渲染的记录。
4. 用 `zen-api-evidence.json` 查看后台实际接收、渠道尝试、流结束状态、写回字节数、最终结果和用量。
5. 用 `request.json` 中的 operationId / traceId，或时间线中的 requestId，关联后台日志。

“已确认”确认的是发生位置，不保证已经找出根因。后台写出响应不等于客户端收到并正确显示。没有查到后台记录，也不等于请求没有到达。

## 判断边界

| 证据 | 判断 |
| --- | --- |
| 本地文件解析、上下文、组件启动、渲染或保存出现明确异常 | Zen AI 对应本地环节 |
| 后台最后一次请求记录了渠道或网关失败 | Zen API 网关/上游，结合渠道尝试进一步排查 |
| 客户端读取完响应，随后解析失败 | 客户端响应处理位置；上游响应是否兼容还需查看错误 |
| 后台成功写出，但客户端未完成处理 | 疑似客户端或返回链路，不假定一定是某一端 |
| 连接/读取中断、写回失败、用户断开、后台证据缺失 | 连接链路或未确认，保留证据缺口 |

每次发送/重新生成使用独立 operationId。模型的工具调用、自动重试、换 Key 和换底座归属于该次发送，不与其他消息混用。已经恢复的早期失败不会被当作最终故障。

上下文整理和正式回答的 HTTP 请求逐一关联，不用前一条整理请求的完成状态判断后一条回答是否接收成功。后台查询返回 `pending` 表示收到过请求，但还没有终态证据，不能直接认定后台卡死。

## 包内内容及隐私

除原有摘要、错误、出错消息及关联用户消息外，增加链路结论、时间线、运行组件/系统信息、有限的关联日志、上下文处理记录、后台证据和收集清单。

Key、Authorization、Cookie、环境变量值及常见字符串密钥统一脱敏。保留输入/输出/缓存 token 数字；长文本保留首尾并标注截断。不会默认导出附件原件和完整对话历史，但出错消息及关联用户输入仍可能包含个人信息，发送前可检查。

ZIP 的 `integrity.json` 包含每个文件的字节数和 SHA-256，可检查文件是否完整。缺失、读取超时、旧版本不支持及有界截断均在清单中说明。

## 部署与兼容

客户端和 API 后台都需要更新，才能获得完整双端证据。不需要数据库结构迁移，也没有新的模型调用费用。

后台新增 `GET /api/client/request-diagnostic`，使用现有 API Key 只读认证；严格限定为同一用户、同一 Key 的请求。兼容禁用/过期/额度耗尽 Key 的现有只读查询规则，但不允许已封禁用户访问。接口不返回其他用户、其他 Key、渠道密钥或原始正文。

旧后台返回 404 时，客户端仍能导出本地诊断，清单注明后台版本不支持，不阻断正常对话。

后台内存保留 24 小时、最多 4096 请求；有消费/错误日志的请求同时附入现有日志，支持重启及多节点查询。没有 requestId 的查询在同一用户和 Key 的最近 24 小时、最多 512 条日志中检索，未命中时明确标注未找到/过期，不能作否定证明。

记录持久化为尽力而为，最多等待 500 毫秒；`persistence` 字段说明是否附入日志。关闭日志、数据库不可用或不存在对应日志时，仍可使用内存证据，但重启后可能缺失。查询合并本节点内存和数据库记录，单次数据库读取限 2 秒。后台重试最多保留 64 次渠道尝试，超出保留首段与末段并报告截断。

客户端后台收集总计限 5 秒、单个响应限 1 MiB。多个 Key 时，只尝试与原请求指纹匹配的现存 Key（最多 3 个）；旧请求没有指纹则使用首个 Key。更换域名或移除原 Key 后明确报告无法查询，不保留明文 Key。后台返回 HTML 等无效内容时，报告证据接口响应无效，不当作模型连接失败。

客户端最多保留最近 100 个发送记录，每进程最多 160 个事件。智能助手的终态记录额外保存在本地诊断目录，便于重启后导出；关联日志限当前进程、当前操作/会话的最近 80 条，并非整份日志文件。

## 人工验收（测试环境）

1. 正常对话：发送“你好，请用一句话介绍你自己。”确认流式回答与原来一致。
2. 失效 Key：在测试 Provider 使用无效 Key，发送同一提示词。导出应包含 HTTP 错误和请求编号，不把它解释为本地渲染错误。
3. 上游全部不可用：在测试后台关闭测试模型的渠道后发送消息。应定位到后台请求/渠道环节，包含尝试记录。
4. 自动恢复：第一个测试渠道失败、第二个成功。回答应正常；后续若发生其他错误，不能仅凭第一条失败认定整个请求是后台失败。
5. 中途断网：开始较长回答后断开测试设备网络。应保留首段响应、已读字节、中断阶段；不能宣称模型一定没生成。
6. 旧后台：用尚未升级后台导出一次错误。应能导出，清单显示接口不支持。
7. 修改 Provider：请求失败后更改服务域名再导出。应显示地址已变化，不把 Key 发送到旧地址。
8. 同一消息重新生成、两个会话同时发送：operationId 不同，证据不串线。
9. 智能助手：正常使用 Codex 和 Claude Code 各一次；若报错，运行组件、实际传输方案、换底座及恢复过程应可查看。
10. 解压并搜索：不应出现测试 Key；用量数字应保留；清单及文件校验应存在。
11. 上下文整理后回答失败：同一轮先让整理请求完成，再模拟回答连接失败。不能因整理请求已完成而误报“完整回答已收到”。
12. 客户端提前超时：模拟上游仍在生成。后台若尚无终态，应显示 `pending`，不要断言未收到请求。

自动测试覆盖脱敏、截断、循环错误、并发记录隔离、流字节一致性、连接/读取失败、归因边界、ZIP 校验与路径校验、后台 Key 权限隔离、持久化和网关异常。真实服务器与 Mac/Windows SDK 网络调用仍需上述验收，不用生产用户请求做故障注入。
