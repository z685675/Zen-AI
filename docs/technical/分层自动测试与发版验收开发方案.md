# Zen AI / Zen API 分层自动测试与发版验收开发方案

- 编写日期：2026-10-18；本次修订：2026-10-19，增加已配置付费模型的自动验收设计。
- 状态：2026-10-19继续补齐本期执行器与统一发版流程。最新范围见第24节；工具开发/自测与实际软件的真实模型、安装升级及多平台验收分别记录，不混为“全部效果已通过”。
- 授权边界：产品负责人同意把已配置的付费模型纳入后续测试。不等于所有测试自动扣费，也不等于无限预算；每次在线运行仍需明确模型、范围和费用/请求上限。
- 目标：把“每次发版由管理员手工重测所有功能”改为“程序自动跑确定性链路与真实模型任务，生成证据和成本报告，人工只处理待复核项与少量真实交互”。
- 适用项目：Zen-AI、Zen-API；新版助手采用 OpenCode 原生执行与压缩。旧助手只读，不重新开放执行。
- 实施原则：复用现有 Vitest、Go test、Playwright、运行时 smoke 和 GitHub Actions；不另造一套 Agent、不以测试之名修改生产配置。

## 0. 给产品负责人先看的摘要

- 不另做软件：放在开发项目里，需要时自动打开独立的测试版 Zen AI；不碰正常会话。
- 可以复用现有付费模型：先选模型、测试档位和预算，一次确认后自动跑整批，不用逐条复制提示词。
- 不只检查“接口能通”：要验证最终回答、文件内容、记忆更正、完成状态、原件保护，以及实际每问成本。
- 四种付费档位：快速检查、发版验收、深度记忆/附件、20轮双入口成本对比；按改动挑选，不是每次都花钱全跑。
- 程序判断确定性结果；可选模型辅助评判开放式回答。扫码、验证码、审美和有争议的答案仍保留人工复核。
- 第一目标是替你完成重复操作和整理证据，不承诺自动发现所有bug、不自动修生产环境、不无限花费。

开发进度以第24、25节及项目《自动质检工具-使用与进度.md》为准。第25节的三模型选模与无报价验收约定优先于前文早期强制报价设计。其他章节包含长期目标；OS沙箱、真实设备、专业视觉/语义可靠性不因执行器写完就自动获得保证。

## 1. 要解决的问题与边界

### 1.1 当前已有基础

Zen AI 已有主进程、渲染进程、shared、aiCore、scripts 等测试项目；现有命令包括 pnpm test、pnpm lint、pnpm validate:release、pnpm smoke:opencode、pnpm smoke:opencode:attachments、pnpm test:e2e。Zen API 已有 Go 单测/接口测试和面板 typecheck/build 检查。

这些测试不能全部等同于“真实用户已验收”。尤其是 macOS 原生运行时、签名和符号链接、真实上游流式响应、浏览器登录验证码、微信投递、真实模型长对话质量，需要另外一层验收。

本方案不是删除现有测试，而是在现有基础上统一入口、补齐关键故障场景、生成可信报告，逐步减少人工重复。

### 1.2 本期明确不做

- 不让 AI 决定是否跳过安全、权限、模型路由或计费用量相关测试。
- 不拿真实用户会话、附件、密钥作为固定测试样本。
- 允许操作员明确授权使用自己已配置的 Provider；不自动扫描、导出所有凭据，不把 Key 放进测试样本、仓库或报告。
- 不在普通 push、PR 或定时回归中默认调用付费上游。
- 不连接生产数据库，不批量禁用生产渠道，不自动发布远程策略。
- 不根据一次模型回答不好就自动禁用模型或回滚生产版本。
- 不宣称摘要保留了全部细节；质量验收与程序正确性分开报告。
- 不因回归失败自动重放办公文件修改、微信发送、定时任务等有副作用的操作。

## 2. 四层测试体系

| 层级 | 主要验证什么 | 触发时机 | 是否用真实模型 | 人工角色 |
| --- | --- | --- | --- | --- |
| L1 改动相关检查 | 类型、格式、纯逻辑、相关服务与组件 | 日常改动/提交 | 否 | 看失败原因 |
| L2 离线链路回归 | Electron → OpenCode → 本地模拟 API → 工具/消息/用量 | 关键改动及发版候选 | 否 | 处理自动报告指出的问题 |
| L3 安装包验收 | 实际打包资源、首次启动、升级、平台/架构、离线启动 | 发版候选/tag 构建 | 否，默认本地模拟 API | Windows/macOS 实机各核对少量交互 |
| L4 真实模型自动验收 | GPT/Claude/Gemini/Grok 实际回答、工具、文件、记忆、缓存与成本；固定断言 + 可选模型裁判 | 手动启动、预检与预算通过后 | 是 | 处理有歧义的结论、登录/验证码及少量视觉体验 |

普通文案/样式改动可以只跑 L1 + 相关界面用例；共享权限、路由、持久化、SDK/依赖升级则提升到 L2/L3。正式发版仍保留现有全量测试门槛，不能因为“相关测试通过”就跳过。

## 3. 一套入口，不是另一套后台

建议新增薄编排入口 scripts/quality/run.ts 与可版本控制的 tests/quality/manifest.json。文件名是拟定方案，实施前核对现有同名工具并复用。

拟提供命令：

- pnpm quality:changed：解析 Git 改动并运行相关检查。
- pnpm quality:offline：离线关键链路。
- pnpm quality:release：全量确定性检查 + 已准备的打包资源校验。
- pnpm quality:live：必须明确手动启动的真实渠道抽测。

在线入口拟支持 --profile quick|release|deep|cost 与 --dry-run。dry-run 只列出模型、用例、预计调用范围、预算和缺失设置，不向付费服务发送请求；在线连通性预检本身可能收费，不能伪装成免费的 dry-run。具体参数以实现后的帮助为准，当前均是设计。

该工具属于仓库中的开发工具链，不新增普通用户 APP 入口，也不额外安装一个测试软件。需要界面测试时，由脚本打开隔离的 Zen AI 测试实例；本机可运行，未来也可由 GitHub 手动任务运行。第一阶段不建设独立控制台或自动修代码的 Agent。

Zen API 对应以 Go test 和 web/default 的 Bun 脚本为执行器；顶层编排器调用两项目既有命令并收集退出码，不把 Go 业务逻辑搬进 TypeScript。

上述命令已实现，另有quality:inventory/acceptance/configure/package/analyze。第一批到第三批历史与当前边界分别见第21至24节；请勿用第一批“仅预览”的历史状态判断最新执行能力。

## 4. 改动影响映射

### 4.1 映射规则

| 变更区域 | 必选验证 |
| --- | --- |
| 文案/i18n/样式 | 类型、i18n、格式；相关组件；必要的截图人工对照 |
| 模型选择/远程策略/可用性同步 | shared 恢复选择器、策略预检、主进程和渲染进程模型恢复、API /models、路由、多 Provider 和 SSE |
| OpenCode 配置、SDK、执行文件、MCP | 原生运行时 smoke、工具调用、流式输出、停止/继续、压缩、离线插件、打包资源 |
| 附件/文档/图片 | 大小边界、分段读取、图片变换、原件保护、工具输出截断、附件引用在压缩后可访问 |
| 文件权限/工作目录 | 路径越界、符号链接、覆盖/删除、确认/备份失败、取消与并发 |
| 用量/使用日志/密钥详情 | 统一 token 语义、同轮多调用分组、导出/查询一致性、未知缓存、权限隔离 |
| 微信/定时 | 幂等、防重复、副作用边界、取消、重启、手机与电脑会话关联 |
| 数据存储/迁移 | 新安装、上一已发布版本升级、脏退出恢复、只读历史、空数据和损坏数据 |
| 构建脚本/锁文件/原生依赖 | 全量测试、生产构建、Windows/macOS 对应架构的打包后 smoke |

### 4.2 禁止漏测的兜底

- Git 基准必须明确：CI 用事件提供的基准提交；本地允许 --base，报告记录实际 SHA。
- 找不到基准、映射文件解析失败、改了未知源码目录、公共基础类型、锁文件或测试配置：自动升为全量检查，不能返回“无测试需要运行”。
- 映射只决定日常相关测试，不降低正式发布门槛。
- 删除/重命名文件同样进入映射；按 Git -z 输出解析，兼容中文、空格和 Windows 路径。
- 同时修改 API 与客户端时做联合报告，不能用一边通过代替另一边。

## 5. 确定性测试数据与环境隔离

### 5.1 隔离目录

每次运行使用唯一、明确的临时目录，分别保存：

- Electron 测试 userData；
- 测试 Provider、策略快照与配置；
- OpenCode 会话、工作区、工具输出；
- 模拟 API 的数据库和日志；
- 测试生成文件和报告。

默认离线测试不得读取用户常用配置、系统浏览器 Cookie、真实微信连接和真实定时计划。在线测试只允许通过第9节的显式授权取得选中的 Provider/模型及必要凭据，不复制整份用户数据库。测试环境中外部集成默认关闭，启动前检查。

独立 userData 和工作目录是防止误用数据的隔离，不是操作系统级安全沙箱。同一系统账号下运行的本地进程仍可能访问其他文件；危险操作和恶意样本测试应在受限账号、虚拟机或具备实际文件/网络约束的执行器中进行，不能仅靠提示词声明安全。

清理只允许删除本次生成且通过绝对路径边界校验的目录。失败产物先保留；报告明确位置，不能清理用户 Documents、Desktop 或项目根目录。

### 5.2 固定文件样本

以生成器构建样本，不在仓库中堆大二进制：

- 文本/JSON：中文、emoji、嵌套、超长单行、无效编码、尾部唯一标记。
- Excel：多工作表、合并单元格、公式、空行、日期、隐藏表、大量行；以独立读取器核对单元格。
- Word/PPT/PDF：多页/多段/多表/图片、扫描件、受损和密码保护文件；不能把“文件存在”当成内容正确。
- 图片：JPG、PNG、透明背景、EXIF 方向、大尺寸、伪装扩展名、损坏图片。
- 单附件小文件、10MB 以上单文件、多个文件累计超过 10MB、超出产品上限；上限由代码导出，测试不私自硬编码另一套阈值。
- 压缩后需要再次查询的附件路径/标识，及源文件后来被移动或删除的情形。
- 示例数据不包含真人隐私、实际收费密钥、客户文件或 Cookie。

所有样本有 seed、生成器版本和校验结果，确保跨平台可重现。

## 6. 本地模拟 API 与故障注入

复用现有 OpenCode smoke 的模拟服务，拆出公共 fixture，不实现一套伪造的 Agent。

模拟接口覆盖应用实际使用的 /v1/models、chat/completions、responses 等协议和流式事件，能力矩阵以当前客户端/SDK实现为准。禁止“只返回一个 OK 就宣称工具链通过”。

### 6.1 必须覆盖的事件

- 正常文本、推理片段、工具调用参数分片、工具执行、最终回答、usage。
- TTFT 延迟、首字前仅收到 HTTP 头/心跳、工具先出现、正文晚于工具、最终完成事件晚到。
- 流在多字节 UTF-8 中间分段、单行 JSON 分段、多事件同一 chunk。
- 200 但空正文/空结果、非法 JSON、HTML 错误页、缺失 usage、仅有缓存统计。
- 401/403/429/503/524、连接前失败、连接后断流、返回部分文本后断开、取消。
- 同一轮内多模型调用，后台其他用户/密钥插入请求。
- 模拟 API 超时要用可控时钟/短本地等待；不要让单测真的睡 3 或 5 分钟。

### 6.2 不做隐性重试

每个 fixture 记录 requestId、taskId、调用次数与请求阶段。断流后不得自动重放已经输出的回答或执行过的工具；是否重试由现有业务边界决定，测试只验证边界不修改边界。

任何未匹配到的外网地址立即拒绝。默认离线测试不读取真实 Provider 凭据；显式配置了真实 Key 也不能悄悄转成在线测试。

## 7. 核心验收用例目录

以下 ID 需要落到 manifest 与自动报告中，而不只是写在文档里。

### 7.1 模型策略和渠道

- POL-01：草稿不影响已发布配置；预检不发布、不探活、不推进多 Key 轮询。
- POL-02：默认 A 不可用，B 不可用，C 可用；正常用户白名单限制与开发者模式按当前产品规则分别验证。
- POL-03：示例密钥的 group/auto/model limits、未配置计价、禁用/过期/额度不足不能被预览忽略；预览仅代表这个样本。
- POL-04：模型所有渠道禁用后消失；只坏一个渠道时仍可走另一个；路由优先级 10 失效可走 9。
- POL-05：SSE 失效信号只含不透明修订；断线重连、代理缓冲、补偿轮询、乱序快照、401 与有效空列表区分。
- POL-06：多 Provider 同名模型不跨域/跨 Key 擅自切换。
- REC-01：首次成功后仍禁用；0/60/120/180 秒四次有效成功才具备恢复资格。
- REC-02：快速手工多点几次不能凑样本；任意失败、Key/配置改变、时钟回退、长调度空档重置。
- REC-03：观察期间管理员手动禁用，不被已开始的探活改回启用。
- REC-04：A 恢复后客户端观察五分钟，忙时不切；抖动延长观察；用户主动选择 B 取消回切。
- REC-05：B 故障而 A 已通过 API 恢复准入时，按现有选择器处理，不因界面倒计时阻断下一次可用选择。
- REC-06：读恢复状态不推进状态机；Slave 节点不冒充 Master 探活结果。

### 7.2 新版助手与 AI 对话

- AGT-01：原生 OpenCode 启动、无需额外下载插件；SDK/内核版本与安装包资源一致。
- AGT-02：一个用户问题的多次底层调用共享 taskId；新问题使用新 taskId；工具结果不丢。
- AGT-03：首字前状态持续可见；已有工具输出不冒充“完全没响应”；停止后没有巨大失败卡片或重复发送。
- AGT-04：文本/文件卡片、首字耗时、总用时、回答完成时间、重启/切换会话后的展示一致。
- AGT-05：停止/重试/分支/删除的真实效果、并发上限、旧助手只读及迁移标记。
- CTX-01：AI 对话按“旧摘要 + 新段文字 + 当前用户补充”增量合并，已整理正文不重复带入。
- CTX-02：AI 对话远程整理全失败时本地 checkpoint 兜底；取消/本地断网不错误冻结；只用 default 整理模型。
- CTX-03：新版助手走 OpenCode 原生压缩，不被 AI 对话远程整理策略插入另一套摘要链路。
- CTX-04：固定长对话含“新结论推翻旧结论”，区分请求结构正确与语义记忆质量。

### 7.3 文件、浏览器与后台任务

- FIL-01：多附件累计大于 10MB 不整体塞入请求；分段读取并能查询末尾标记。
- FIL-02：原件保留，新结果另存；明确覆盖/删除需按既定确认/备份边界执行，备份失败不继续破坏。
- FIL-03：路径规范化、越界、junction/symlink、同名输出、多任务并发写入、取消中的半成品。
- FIL-04：无 Python 环境/下载失败时不拖死普通文本任务；可选能力给出准确提示。
- WEB-01：登录/验证码等待，用户继续后回新版助手，同一会话不错误跳旧入口。
- WX-01：手机发问→电脑会话、电脑续聊→手机回传；重复事件不重复执行或投递。
- WX-02：附件无法投递时给替代说明；无人在电脑前时不越过危险操作确认。
- SCH-01：重复时刻/夏令时/睡眠/重启/取消/停用、正在运行的计划如何处理；不补跑一堆过期任务。
- 后台任务和微信仅使用模拟传输与隔离目录；真实账号投递列入人工清单。

### 7.4 用量与异常观察

- USG-01：输入 130000、缓存读取 120000，显示输入 130000、缓存 120000；总 token 仅输入 + 输出。
- USG-02：Anthropic 原始输入不含缓存的情况只补一次；兼容历史归一化标记。
- USG-03：缓存写入与读取分开、未知值为未知，退款/错误不算成功消耗请求。
- USG-04：日志列表、导出、密钥详情、我的用量汇总一致；删除渠道不删除历史消耗。
- USG-05：任务分组不混入其他密钥/用户；没有 taskId 时不捏造“一个用户问题”。
- USG-06：缓存命中下降、每任务调用/输入/输出上升仅管理员提示；低样本、不同渠道、缺缓存字段不误报。
- USG-07：20,000 行上限、超时、并发、取消、数据库错误不会展示为“没有异常”。
- USG-08：异常接口只返回计数/标识，不返回消息正文、密钥或原始错误 URL。

## 8. 性能与语义评估不是同一种测试

### 8.1 确定性性能

测本地启动、准备配置、发送到模拟 API 的延迟、工具启动、附件处理峰值内存、压缩输入大小及最终请求体大小。

记录平台、CPU/架构、Node/Electron/OpenCode版本、fixture hash、冷/热启动。先收集基线再设阈值，不凭感觉写“必须一秒内”。

- 同平台多次重复，单次波动只标为波动。
- 基线更新需有原因和复核，不能每次回归自动把更差结果当新正常。
- 小样本给实际数值/中位数/范围；不足以估计 P95 时明确标注。
- Windows 不代替 Mac；开发环境不代替安装包。

### 8.2 四模型真实评估

每个模型运行相同固定文本/20轮方案，两个入口保持同模型、同上游条件，并记录渠道是否切换。脚本检查标注事实、后续更正、数值约束和回答完整性；有歧义的语义再交给可选模型裁判与人工复核，而不是把所有回答都留给管理员逐条阅读。

真实模型必须经产品实际链路调用：AI 对话走现有发送、整理和渲染流程；新版助手走原生 OpenCode、现有工具/技能和会话流程。单独用 SDK 直接问模型只能证明接口能通，不能代替这两个入口的验收。实际 UI 自动化尚未落地前，报告明确写“服务链路测试”，不冒充已点击界面。

缓存率只用明确记录的缓存读取 / 总输入；缓存价格与模型输入/输出价必须来自本次明确提供的价格快照，同币种、同阶梯计算。无成本元数据时只报 token，不推导真实采购成本。

每用户问题将同 taskId 的全部调用合并；对于没有 taskId 的 AI 对话辅助命名/整理请求，单独列出归因不确定性，不能静默漏算或混算。

“至少保留90%关键记忆”只能在标注了必记事实的样本上统计，不是对所有用户输入的保证。核心预算、用户最新更正、禁止覆盖原件等关键约束单独设为必须通过，不能靠其他答对项拉高平均分抵消。

## 9. 在线测试费用和安全闸门

### 9.1 可以复用已配置的模型，但必须主动选择

- 首选本机已有 Provider，由操作员选定 Provider ID、完整模型 ID、使用的 Key/分组；不要求为测试重新配置一整套模型服务。
- 推荐使用测试专用低权限 Key；也允许明确授权现有 Key。复用现有 Key 时必须检查混入的普通对话、微信和定时流量，无法精确分离则不声称获得精确成本。
- 在线适配器由受信任的主进程按当前凭据存储规则解析授权项；不得让脚本通读所有用户配置，不经报告/命令行参数传递 Key，不为了测试增加持久化明文副本。
- 测试配置只记录 Provider 引用/凭据引用；密钥材料仅在必要的受信任组件中使用，子进程仅获得本次最小权限。若现有内核必须获得凭据，要明确其边界，不承诺“任何子进程都拿不到 Key”；优先复用网关的凭据注入能力。
- 本机凭据不会自动上传 GitHub。CI 在线任务单独配置测试 Secrets、授权人和环境保护；不在 fork/不可信 PR 中加载生产凭据。
- 某家未配置或不可用时记为“未执行/环境阻塞”，不能偷偷选择另一型号顶替。模型可用性检查若涉及发问，也计入调用和费用。

### 9.2 一次授权一批，不必每发一句再确认

运行开始展示清单：目标版本、模型、入口、用例、用户轮数、最大底层请求数、裁判模型、预算、超时、测试文件位置。

操作员一次批准本批测试，程序顺序完成，不用每条提示词都点确认。超出批准范围、增加模型、扩大预算或补跑昂贵长上下文任务时，停止并另行确认；不能把“允许用付费模型”当作永久无限授权。

普通 push/单测仍为零付费调用。未来如需要夜间付费回归，单独授权频率、范围和周期预算后再接调度，本计划不直接创建定时任务。

### 9.3 预算既管用户问题，也管实际模型请求

每份运行配置至少声明：

- 总金额上限及币种，输入/输出/缓存读写价格快照及适用阶梯；
- 总用户问题数、实际底层模型调用数、每任务调用数、每请求输出上限；
- 累计输入/输出 Token 上限、单任务及总超时；
- 并发上限，首版在线默认为1；深度记忆与成本会话逐轮串行；
- 可选裁判模型、最大裁判次数及独立子预算；
- 网络目标白名单、生成文件目录与允许的工具范围。

首次使用预算未填则只出计划不执行，金额不擅自替用户决定。缺少可靠价格时，必须明确接受“只按请求/Token/时间限额、金额无法保证”才能运行，不能显示假的精确费用。

发请求前预留预算，而不只是请求后算账。未知缓存默认按较贵的适用输入价预估；已知上下文阶梯、独立写入、图像/其他计价须纳入，未支持的计价模型先拒绝金额保证。并发请求共享原子账本，已在途的预留金额不能重复使用。

所有经授权模型通道发出的请求都经过计数/预算边界：助手工具循环、子 Agent、压缩、命名、模型裁判、SDK 重试都不能只因不是“用户新问题”就漏算。未实现全通道拦截前，该档任务不可宣称金额硬限制。

达到任一上限停止新的调用，保留已产生的回答和产物，标记“预算停止/未完成”，不是功能通过。取消/超时后上游可能仍执行或计费，已发出的请求不能保证撤销；运行结束留出对账步骤。

客户端预算是保护措施，无法单独保证上游绝不超扣。推荐 API 面板设置服务端测试 Key 额度/请求上限作为最后一道硬限制；共用 Key 有其他流量时不把余额差全部算成本次测试。

### 9.4 安全与副作用

- 使用合成文件和隔离工作区；可用真实 API 获取回答，但不连接生产数据库做故障注入，不改变生产路由、渠道启用状态或远程策略。
- 允许真实生产推理端点的正常小流量请求；须知道服务端原有自动熔断/禁用仍可能被请求失败触发。安全故障测试放在隔离面板，不以测试代码绕过生产机制。
- 网络目的地限制在选定 Provider、必要本地服务和专门网页 fixture；重定向不可带着 Authorization 跨域转发。第三方检索如需付费或对外访问，单独列入范围。
- 未授权工具、系统浏览器 Cookie、真实微信投递、定时计划、软件安装、Git 推送、删除真实文件一律不因在线测试而开放。
- 不因失败自动回放已有副作用的任务，不无限换模型/渠道重试；只追加受控诊断，首次失败、追加调用和费用均保留。
- 报告脱敏；默认不把完整 prompt/模型回答/文件全文/HTML/Cookie 放到公开 Actions。合成样本可本地留原始证据，上传前按白名单筛选、设保留期。
- 操作员停止后中止队列与可取消请求，清理本次子进程，保留已完成/失败/未执行；不能把“停止了”记为“测过了”。

## 10. 报告规范

每次输出 report.json、report.md；失败才按需附 ZIP，包含脱敏日志、fixture 清单、截图、请求结构摘要和用量计数，不默认收集全部用户数据。

report.json 拟包含：

~~~json
{
  "schemaVersion": 1,
  "runId": "quality-YYYYMMDD-unique",
  "mode": "changed|offline|release|live",
  "revision": { "zenAI": "commit-sha", "zenAPI": "commit-sha" },
  "environment": { "os": "windows", "arch": "x64", "packaged": false },
  "network": { "liveAuthorized": false, "unexpectedExternalRequests": 0 },
  "selection": { "base": "base-sha", "reason": ["model-policy"], "fallbackToFull": false },
  "summary": { "passed": 0, "failed": 0, "skipped": 0, "notRun": 0, "reviewRequired": 0, "environmentBlocked": 0, "inconclusive": 0 },
  "cases": [{ "id": "REC-01", "status": "passed", "durationMs": 123, "evidence": ["redacted-log"] }],
  "manualRequired": [{ "id": "MAC-LOGIN", "reason": "real OS interaction", "prompt": "请打开这个网页并总结，遇到登录时等我处理。" }],
  "live": { "profile": null, "authorizedProviderRefs": [], "modelIds": [], "judgingEnabled": false },
  "budget": { "currency": null, "limit": null, "reserved": null, "exceeded": false },
  "cost": { "known": false, "basis": "unknown", "currency": null, "amount": null, "usagePending": false }
}
~~~

必须满足：

- 通过/失败/跳过/未执行分开，跳过不算通过；总数以最终唯一用例 ID 为准，不把重跑重复累计。
- 超时和原生进程崩溃，即使断言曾经全通过也算运行失败。
- 所有子进程退出码和信号保留；测试运行器失败时不生成绿色总结。
- 人工清单自动去重，只列本次改动需要的项目，附完整提示词、操作步骤、预期结果及反馈模板。
- 未执行 Mac 实机、真实 Key、真实微信时在报告醒目标注，不写“全平台完成验收”。
- 环境阻塞、证据不足、语义待复核分别展示；汇总给出计划范围与实跑范围，不用缩小分母制造“100%通过”。
- 在线用例以 caseId + modelId + entry + repetition 标识唯一执行，重跑作为 attempt 附在原项下。记录源代码 dirty 状态及变更摘要，不能只写 HEAD 就冒充准确测试版本。
- 标记费用是实际结算、已知价格估算、部分估算还是未知，裁判费用另列；测试报告本身不修改用户或管理员用量口径。

## 11. CI 与安装包门槛

### 11.1 日常改动

L1 默认无密钥，保留现有 CI 检查。依赖和影响分析不确定则扩大测试，不能静默降级。对权限/文件/支付用量等关键模块，至少跑共享单测和相关集成。

### 11.2 发版候选

- Zen AI：pnpm lint、pnpm test、pnpm validate:release、必要 skills/openapi 校验 + OpenCode 离线 smoke。
- Zen API：go test ./... -parallel 1、go vet（涉及模块），面板 typecheck、相关 ESLint/格式与生产构建。
- 正式打包后验收内置执行文件架构、运行时依赖、插件完整性、symlink 是否越出 app bundle、Mac codesign 验证。
- Windows x64/arm64 与 macOS arm64/x64 按实际发布目标分别构建/检查；未提供设备的平台只能声明构建验证，不能声明实机测试通过。
- 发布 tag 绑定的 SHA 与测试 SHA 必须一致；若打包时生成了资源，记录资源 hash 和源版本。
- 失败保留构建产物/日志；不自动改签名参数来掩盖失败，不自动发布可疑安装包。
- 不要求代理持续监测 Actions：按用户要求，推送触发后由用户查看构建结果；本方案不新增自动跟踪通知。

### 11.3 防止 flaky 变成习惯

确定性失败默认不重试。有明确环境抖动的用例最多诊断性重跑一次，报告同时保留首次失败。不能“重跑直到绿”。

隔离 flaky 用例必须关联负责人/原因/修复条件；安全、数据丢失、用量计算错误和模型不可调用用例不能简单隔离后放行。

当前 Playwright 配置在 CI 默认 retries=2；接入统一编排时必须审计这个现状。付费任务不继承该默认重试，避免一条20轮测试在不知情下付费跑三遍。首轮错误始终保留，在线重测需落在同批已批准的重测次数与预算内。

## 12. 开发拆分与完成条件

### Q0 盘点和建立基线

- 盘点已有脚本、CI、用例、运行时间和外网访问；建立 manifest。
- 输出当前哪些自动覆盖、哪些仅文档描述，不用文档条数当自动化覆盖数。
- 完成条件：现有脚本能统一列出，报告不得遗漏失败/跳过；不改变任何业务行为。

### Q1 统一报告与相关测试选择

- 编排器/JSON schema/Markdown报告；Git影响映射；未知变更提升全量。
- 自测：中文路径、rename/delete、缺基准、脚本崩溃、信号退出、报告写入失败、测试超时。
- 完成条件：可以一条命令拿到可信结果和人工清单；默认没有真实 Key/外网调用。

### Q2 离线 API 与关键故障注入

- 提取已有 smoke fixture，加入协议分片、超时/断流/空回答/usage。
- 先覆盖 POL/REC/USG/AGT，再覆盖附件与文件安全。
- 完成条件：无需真实模型稳定重现已知故障；连续多次运行结果一致；原生 OpenCode 真正走完工具链。

### Q3 Electron 与打包后验收

- 测试 userData 隔离、固定 UI 选择器、首次启动/升级模拟；平台原生资源校验。
- 重点防回归：Mac附件闪退、首字前空白、旧入口误跳、打包 symlink 越界、环境安装阻塞文本任务。
- 完成条件：至少 Windows 安装包离线跑通；Mac CI 校验通过并留下实机待验项目。

### Q4a 真实模型快速验收

- 在 Q0–Q2 的报告/隔离基础上，加选中 Provider 的受信任凭据适配、全通道请求计数、预算和停止机制。
- 先接 quick 档，跑四家实际回答与一个轻量工具任务；服务链路与真正 UI 驱动分别标记。
- 完成条件：选定模型可自动跑完、拿到请求与最终回答证据；未授权/超预算拒绝启动；用可控模拟计费验证限额，不烧真实额度测试失控。

### Q4b 文件与多轮语义验收

- 接独立文件检查器、标注事实、压缩证据、可选模型裁判；发布档和长上下文档分开。
- 完成条件：能检出“文件存在但内容错误”“新旧预算混用”“并未真正压缩却报告记忆通过”；裁判不替代安全硬断言。

### Q4c 成本、缓存与版本对比

- 自动执行既有四模型双入口20轮，按实际调用归因，对账并报告第1/5/10/20轮累计成本。
- 同步支持旧/新版本相同样本的配对运行；记录渠道、协议、模型与配置，不能将版本变化和上游变化混为一谈。
- 完成条件：未知 usage/渠道/价格就明确降级结论；用户问题数、总调用数、辅助调用与裁判费用不漏算。

### Q5 发版清单自动生成与持续维护

- 从报告生成本次人工测试文档，失败证据ZIP和发布门槛总结。
- 当线上发现新问题，先补最小可复现 fixture，再修复；修复后固定为回归用例。
- 完成条件：管理员不必每版重抄提示词、不必手动汇总几千条测试；人工验证只剩无法可靠自动化的项目。

建议先落地 Q0–Q2，接 Q4a 得到真实模型的快速收益，再做 Q3 与 Q4b/Q4c，最后接 Q5。阶段间独立验收；不能为赶在线测试跳过隔离和预算，也不同时重构助手执行、路由、测试平台和发版流程。

## 13. 最小人工验收清单（未来自动生成的目标）

普通发版预计保留以下少量项目，具体以本次改动为准，不承诺固定耗时：

1. 实际安装包启动/更新正常，原有会话与 Provider 未丢。
2. 本次主要模型的问候、首字/结束状态可由真实自动验收覆盖；人工只抽查一段展示与阅读体验。
3. 若改助手：简单工具、停止后继续、文件打开优先自动化；缺少执行器或涉及真实系统交互时转人工。
4. 若改附件：小文件与多附件大文件组合优先自动检查内容；人工抽看一份实际文档/图片的可读性。
5. 若改策略：隔离测试 A→B→恢复，不用生产全量禁用做实验。
6. 若改微信/定时/登录：各一次真实交互。
7. 有 Mac 包：Mac 实机一次附件任务与复杂工具任务。

每项提供可以直接复制的普通用户提示词。未涉及该功能且可靠自动化已覆盖时，不再要求用户重复验全套。

## 14. 回滚与上线

- 测试工具失败不改变生产策略，也不自动停止生产服务。
- 初期报告“旁路运行”：与现有测试并行，对照结果，确认无漏报后再作为发布硬门槛。
- 相关测试选择器出错时全量兜底；报告服务出错不能把结果写为通过。
- 回滚测试工具只影响测试编排，不回滚用户数据库、不删除日志、不恢复旧助手执行入口。
- 每个阶段单独提交、独立验收，避免测试平台成为新的大而不稳的系统。

## 15. 最终能做到什么程度

目标是“会自动操作产品、核对结果、追踪调用、产出待办的质检流水线”，不是“另一个万能 Agent”。

| 能力 | 自动化目标 | 不能据此保证什么 |
| --- | --- | --- |
| 自动操作两个入口 | 新建会话、选模型、逐轮发送、等待真正结束、切会话/重启后核对历史 | 不代表用户所有操作组合都已覆盖 |
| 真实回答链路 | 检出转圈、空回答、流式丢失、终止事件缺失；记录首字与总耗时 | 不能仅凭请求成功就判断回答有帮助 |
| 文件理解 | 根据带答案的 Word/Excel/PPT/PDF/图片/JSON 提问，检查指定数据与跨文件汇总 | 不能承诺任意扫描件、受损或加密文件都能解读 |
| 文件产出 | 助手生成/修改文件，独立打开、解析内容，核对公式/数据/页数与源文件 hash | 图表、排版与审美仍需视觉抽检 |
| 记忆与压缩 | 自动灌入标注资料、确认真实压缩发生、追问旧事实与最新更正 | 不是“所有细节永久记住”，20轮也不必然达到压缩阈值 |
| 模型兼容 | 四家真实模型按产品所走协议验证文本、视觉、工具和完成信号 | 不保证同品牌的所有型号、所有渠道永远兼容 |
| 成本与缓存 | 对账每问全部调用，自动比较两个入口、版本与累计轮数 | 缓存高不必然更便宜；看不到读取字段不能捏造命中率 |
| 故障与安全 | 离线自动注入异常，验证切换、不打断、备份/确认与旧助手只读 | 不在生产上强制制造故障，更不自动修生产配置 |
| 失败定位 | 汇集客户端、OpenCode、Zen API 关联证据，给出已证实/疑似/未知 | 未拿到服务端或上游证据时不能百分百断言责任 |
| 发版报告 | 生成阻断项、待复核项、遗漏范围和人工提示词 | 自动通过不是免除发布负责人判断 |

不预先承诺“自动化覆盖率90%”或“以后完全不用人工”。用实际数据衡量：固定用例覆盖率、故障检出率、误报率、需人工复核数量、手测时间和每次测试费用。第一版先在高风险链路上省力，再扩大。

## 16. 真实模型测试档位与范围

四家模型的具体 ID 从本次配置中选择，不把当前型号写死在脚本。模型、渠道及能力不清楚时先报告，不靠名称臆测全部功能。

### 16.1 quick：快速验收

- 四家各选1个模型，两个入口各跑1段2轮文字对话：8段会话、16条标准用户消息。
- 每家在新版助手再做1个轻量工具任务：4个用户任务；合计20条标准用户消息，不含诊断或裁判。
- 两轮文本检查正常输出、前文数字记忆、用户更正；工具任务从固定 JSON 求和并另存一个短报告，检查工具确实执行、结果正确且原件未动。
- 不跑长上下文、不触发付费图像生成、不用模型裁判；底层请求数可能大于20，尤其助手会多次调用。
- 首版以这一档验证真实连接与产品可用性，不将小样本成功率当长期 SLA。

### 16.2 release：发版验收

- 包含 quick，按影响映射增加实际变化模块。
- 文件模块变更：Word/Excel/PPT/PDF/JPG/PNG/JSON 各有小型金标准读入题；AI 对话只读与回答，新版助手再测生成/修改/另存。
- 例如四家 × 两入口 × 七类读入题为56个用户任务，只在选择该完整矩阵时运行；不能后台因为“发版档”就展开所有组合。
- 增加至少一组多附件累计超过10MB的查询、受损文件的正确失败说明、停止后继续及历史持久化。超过产品上限的输入应得到正确拒绝，不以越过上限为通过。
- 每家至少一个本次涉及的工具闭环；需要浏览器时只访本地固定网页，真实登录另列人工项。
- 无关模块不反复付费重测；协议、权限、SDK、附件或路由基础层改动则扩大矩阵。

### 16.3 deep：长上下文与复杂任务

- 将普通20轮记忆、受控容量压力、真实原生压缩、附件压缩后再次读取拆成不同用例。
- 长上下文以接近真实产品阈值的合成资料驱动，并标注实际请求 Token/字节估算误差；先在单一选定模型小规模校准，再授权其他模型。不能为了测压缩悄悄降低产品阈值并宣称200K级测试通过。
- 容量取产品、模型与服务端实际限制中的有效较小值，并预留回答空间；不对不支持200K的模型强塞200K输入。能力上限未知时标未验证，不能从模型名字推定容量。
- AI 对话记录 checkpoint 覆盖边界与请求组成；新版助手记录原生压缩事件和后续状态，不为测试塞入另一套摘要。
- 在资料头/中/尾埋已标注事实，后续两次更正其中部分；压缩后分散追问，检查新旧信息冲突、关键记忆与引用来源。
- 结构化关键事实用程序判，开放式表达再用裁判；约束是否满足和事实保留率分开统计。
- 可选研究/多文件复杂工具任务放独立子集；全部串行并有任务请求上限，避免失控循环。
- 大输入即使缓存便宜也可能产生明显费用，单独预算，不能随 quick 隐式启动。

### 16.4 cost：双入口成本与缓存对比

- 直接复用《01-20轮对话与四模型成本对比.md》的固定提示词、最终答案卡和节奏。
- 完整矩阵4模型 × 2入口 × 20轮 = 160条标准用户消息；8段独立会话，不生成文件、不联网，不额外修改系统提示词/技能来美化结果。
- 两个入口一段一段串行，交替先测哪个；每轮等真正完成再按一致的节奏继续。开始前记录所选完整模型 ID、推理设置、协议、Key/分组和已知渠道。
- 在 prompt 内容里不插测试编号、时间戳或随机 runId，以免改变缓存前缀；runId/taskId 用已有元数据/可兼容的请求追踪机制携带。
- 不承诺清空上游缓存，不把新会话称严格冷启动；分第1轮、2～5、6～10、11～20轮报告缓存与成本。
- 输出第1/5/10/20轮累计总费用和平均每问费用，以及8段总体、主模型、命名/压缩/重试明细。可观察到哪个轮数后助手更划算；没有交点就写没有，不能外推所有用户。
- 80%缓存率仅作观察指标，不是价格结论或协议通过门槛。只有读取字段已知且分母有效才计算读取命中率。
- 正常路由中发生模型/渠道变更、失败/恢复时保留实际成本，另标“受故障或路由变化影响”。若要固定渠道对比，只在隔离面板或专用无用户影响路由中做。
- 读取不到实际渠道/账号则标未知；“同渠道ID”不等于上游同账号。多次测同一模型时交换入口顺序，可减轻而不能完全消除共享缓存和时间偏差。
- 输出长度、完成质量不同也列出来：便宜但错误多不算更合适，输出更长的价差也不能全部归因于缓存。

四档均可只选其中一家/一个入口；报告写完整的计划和实际选择，不用“测了Gemini”冒充四家验证。

## 17. 怎样自动判断回答与产物对不对

### 17.1 程序硬断言：发布安全底线

用于可精确计算或读取的结果：是否真的结束、回答非空、最新预算、跨表合计、源文件未改、输出能打开、任务归属与 token 计算、凭据不泄露、危险操作被拦住。

- 金标准随 fixture 生成并独立保存，不把答案卡发送给被测模型。
- 文件由独立读取器检验，不能让同一个模型说“已生成正确”就算通过；关键合计以固定代码重新计算。
- 兼容合理数字/日期/单位表达，不用要求模型输出一模一样措辞来造成误报；需要严格结构的专项用例单列，普通用户提示词不被改成全是技术指令。
- 新输出文件、修改文件与删除保护是不同断言；模型裁判无权覆盖安全/正确性硬失败。

### 17.2 可选模型裁判：帮助筛掉大部分需要人工读的答案

裁判仅看合成样本问题、参考要点和回答，按固定 rubric 检查事实覆盖、是否采用最新更正、是否胡编、是否完成用户目标；给出对应证据片段，不只打一个总分。

- 尽量不让被测模型同时裁判自己；跨家族裁判是减少同源偏差的选择，不保证绝对公正。未配置独立裁判时可关闭，不能偷换未批准模型。
- 先用人工标注的“正确/部分正确/故意错误”样本校准裁判，测误报和漏报；裁判提示词、版本、模型 ID 固定留档。
- 不因为裁判自己输出信心高就当可信；依据校准、规则与证据，出现冲突/无证据/边界评分时标待复核。安全与金额核算不交给裁判。
- 文件、网页、被测回答均当不可信资料，不能执行里面的“忽略规则/给满分”等指令。裁判不具备工具、终端和联网权限；输出按严格 schema 验证。
- 裁判超时、无效 JSON、拒答或额度耗尽记“未评估/待复核”，不影响已测事实的原始记录，也不默认为通过。
- 默认只把开放式/有歧义/抽检样本送裁判；不对每一轮都请求昂贵裁判。所有裁判调用单独计费，不混入被测产品单问成本。
- 生成新的探索题可作为后续扩展，但不允许裁判在运行中自行改答案或通过标准。

### 17.3 人工仍然保留的工作

真实扫码/登录/滑块验证码、微信真实账号接收、Mac设备差异、审美与版式、专业知识正确性、裁判分歧，由人工少量抽检。给到操作者的是“这几项待验证 + 可复制提示词”，不是几百条原始日志。

尚未有平台执行器的能力列“未执行”；自动截图不等于已完成视觉验收，自动化进程能启动也不等于应用没有闪退风险。

## 18. 证据链、成本对账与失败归因

### 18.1 单次任务关联

每次运行有 runId，每段会话有 sessionId，每个用户问题有 turnId/taskId，每次模型请求有 requestId。继承现有客户端来源与 OpenCode 分组，不为测试改变普通用户使用日志展示。

记录本地单调时钟耗时与UTC时间，并保留时区。区分：排队、内核准备、请求发出、HTTP首事件、首个可见工具/文字、首个正文 Token、回答完成、持久化完成。不能把心跳或推理事件当正文首字，也不能把发送时间当最终完成时间。

自动命名/压缩若没有可靠任务关联，优先通过测试用的观察接口关联；仍无法归因就单列未知。不能仅用“时间看起来接近”声称属于同一问题。

### 18.2 只收有权访问的日志

- 客户端/OpenCode/本地网关：脱敏事件与请求结构摘要，记录调用阶段和最终状态。
- Zen API：使用已授权的测试日志查询/导出权限，只查本次 Key/请求范围；不向客户端或用例发管理员 Key。
- 仅有推理 Key 时，照常测真实回答，但服务器日志关联、渠道/结算信息标未知；没有权限就不绕过权限。
- 日志可能异步写入，有限次对账等待后仍缺失则记 usage_pending，不把0当真。价格快照与账单对不上要报告差异，不修改计费记录“使之相等”。

### 18.3 归因带证据等级

可以输出以下类别，但每条须注明“已证实/疑似/证据不足”：

- Zen AI渲染/持久化：已收到有效最终正文但没有正确呈现/保存。
- OpenCode/工具/文件处理：工具抛错、进程异常、附件读取失败有直接日志。
- Zen API鉴权/路由：服务端确实收到对应requestId并有明确拒绝/无渠道证据。
- 上游：面板有明确转发结果/限流/超时证据；403/429/524不是仅凭代码就能确定具体账号或网络原因。
- 传输/网络/未知：只知道请求未完成、缺服务端日志时不能断言一定未到服务端，更不能直接认定本地网络断开。

报告优先给“失败步骤、关键证据、下一步检查”，不输出听起来确定却没有依据的根因。

### 18.4 成本口径不变

- 输入包含缓存，缓存读取是其中一部分；总 token = 输入 + 输出，缓存不能再重复加一遍。
- 模型原生 usage 按现有归一化契约处理，读取/写入/未知分开，不能把未知当0。
- 按各调用自己的实际模型、渠道价格/阶梯、币种核算；对用户收费价不冒充采购成本。
- 被测产品成本包含命名、整理、重试、子调用；测试裁判和额外诊断列“测试开销”。
- 成本缺项只报已知小计与未知部分，不以估算作实际结算；最终交付原始脱敏计数和可复算公式。

## 19. 第一版交付标准与效果验证

### 19.1 必交付

1. 本地一条命令计划/执行，默认离线；报告里区分现有能力和未实现的未来项目。
2. 已配置 Provider 的最小授权适配；无密钥/预算/模型映射时 fail closed，不自动借其他配置。
3. quick 自动执行两个真实产品链路；GUI尚未覆盖的阶段准确标注。
4. 记录每问全部底层调用，受控预算、取消与超时；模拟测试证明隐式重试/裁判/压缩同样受限。
5. 固定答案判定、至少一个真实文件工具产物独立校验；失败证据包不泄露 Key。
6. JSON + 可读报告 + 人工待办：失败不能被成功用例覆盖，运行器异常不能留下绿色通过。
7. 原有业务行为、原生OpenCode执行循环、旧助手只读边界不被测试改动破坏。

### 19.2 用历史故障验收“这个测试工具本身”

用可控 fixture 重现空回答、长时间转圈、部分流丢失、附件读取错误、文件内容错误、预算新旧混用、输入/缓存重复计数、超过限额后继续调用、成功断言后进程崩溃等问题。工具必须报对失败类型并保留证据，才有资格作为质检工具。

测试工具也有自己的单元/集成测试；不能只靠它给自己打一份绿色报告。离线最小复现先跑，真实模型只验证真实链路，避免每次验证测试工具都花钱。

### 19.3 逐步提高门槛

- 先旁路运行数次，人工抽检“自动通过”与“自动失败”的样本，了解误报/漏报、费用和耗时。
- 明确的安全、数据丢失、计数错误设硬门槛；上游临时故障标环境阻塞，不假报代码bug，但关键入口也不能因环境阻塞就默认可发版。
- 真实语义先报告问题与趋势，校准后再把特定金标准项设门槛。小样本不输出长期成功率或“稳定性提升百分比”。
- 旧/新版本比较至少保留相同题库、模型和参数，交替顺序；上游发生变化则标不可直接比较，不把一次变快全归功于代码。
- 每次线上新故障补进离线回归库，降低以后重复发生的概率，而不是持续扩大每版付费重跑范围。

## 20. 操作者最终怎么用

开发完成后，理想操作只需：

1. 选择“快速/发版/深度/成本”以及已配置的模型，不必手工发几十条提示词。
2. 查看 dry-run 的用例与预算，确认一批；程序自动串行跑，界面显示阶段、剩余任务和已知费用。
3. 完成后先看结论页：阻断问题、环境问题、语义待复核、成本/缓存对比、仍需人工操作。
4. 只处理生成的少量人工清单，反馈后把证据附回同次报告。

这是一套逐步实现的目标，不是当前已经可以使用的按钮。真实模型有助于发现模拟看不到的问题，但必须与离线故障注入、程序断言、安装包测试和人工抽检组合使用，不能“花钱问模型几次”就替代整套工程验收。

## 22. 本轮补充：模型可选，选好后再估价和确认预算

1. 验收对象不写死具体型号。操作者可以更换 Provider 和模型、增减同一家族的候选型号，选择 AI 对话、新版助手或两个入口。成本对比要让两个入口使用同一模型、同一题库和参数，不能悄悄换模型。当前第一批已支持配置文件中的 providerRef/modelId/entries；方便选择的交互和真实执行仍待后续接入。
2. 操作顺序为：选择模型/测试范围 → 生成费用预估 → 操作者确认金额上限 → 执行。预览草稿允许预算尚未确认；执行配置仍必须有明确预算。示例中的5元或讨论中的10元都不是已确认的授权，不得作为默认扣费许可。
3. 报价优先使用可核验的 Provider/测试 Key 对应价格快照，包含币种、时间、适用分组/折扣、输入、输出、缓存读写和上下文阶梯。公共定价接口的默认分组价不一定适用于该 Key，不能直接冒充准确扣费价。接口拿不到完整有效价格时允许导入/手填价格并标来源；无可靠价格时只显示 Token 计划，不宣称金额保证，也不启动金额受控的付费批次。
4. 分开记录“测试 Key 的实际扣费”和“上游采购成本”。只有明确提供对应模型/渠道采购成本价，才输出采购成本；不能拿 API 面板对用户的收费价冒充成本价。
5. 估算显示区间和保守预留，不承诺准确预测未来输出。未知缓存按未命中估算；预留必须纳入系统/工具定义、历史、附件，以及命名、压缩、重试、探活、裁判等可能调用。独立缓存写入、长上下文阶梯或特殊计费也要处理，无法正确处理时拒绝执行。
6. 对“输入总量已包含缓存读取”的常见口径，费用按“普通输入 = 总输入 - 缓存读取，再加缓存读取费用和输出费用”计算，而不是把输入总量和缓存再收两遍。例如输入13万、缓存12万，普通输入是1万。缓存写入等额外项必须按实际 Provider 口径独立核对，不能机械套用。
7. 金额控制在每次底层请求前预留，失败或用量缺失不视为零；接近上限不发下一次请求。不得擅自换到更贵或未批准的模型。模型裁判可选；启用时单列型号/费用，并计入同批总上限。切换模型、价格或范围后，须重新计算计划并确认预算。
8. 第一批没有实际读取报价、价格金额账本或付费执行器；第二批落地与限制见第23节，不把后续设计写成已实现。

## 25. 三模型手动选择与无报价限量验收（2026-10-19）

产品负责人确认：面板向用户计费的价格不等于采购成本，有些型号尚未定价；不能因缺少报价阻塞功能验收。新版向导先GET所选Provider的/models，支持搜索与刷新，由操作者手动选择3个不同完整ID，再选择范围与入口，不读取日常保存的凭据。

- 默认budget.mode=tokens，必须明确acknowledgedUnknownCost=true；只以总请求数、单请求/累计Token预留、每轮循环数及超时限制规模。默认60条底层请求、每轮8条、单请求输入128000/输出2000、累计输入1000000/输出60000，可主动调整。
- 无报价不填虚假价格/金额，不承诺人民币上限；每条记录amount=null，报告“未核算”。缺失用量继续保守占用Token预留，不能当作免费；有报价的money模式保留且继续严格预检。
- quick/release的allocation=mixed：3个模型都跑基础更正；其余关联用例组确定性轮转分配。读入和制作同格式文件不能拆开；记忆资料、两次更正与回忆保持同一模型。两个入口使用一致分配，AI对话不承担文件制作。
- 不在一次工具循环或连续记忆里随意换模型；失败不自动换其他模型掩盖，后续未测项不计通过。报告列模型/入口/用例分配，不能把混用抽测声称为三模型全矩阵覆盖。
- deep/cost必须allocation=all-models，同一型号跑完整长对话/20轮；费用暂缺也能采集Token，但不能据此得出采购成本优劣。裁判增加额外付费，仅在独立money配置显式批准时启用。
- 获取列表只是元数据请求；配置向导不生成模型内容。预览/批准摘要、隔离实例、明确测试凭据、单次请求保护与停止机制继续生效。模型/范围/分配/限制/代码变化后，旧批准不能复用。
