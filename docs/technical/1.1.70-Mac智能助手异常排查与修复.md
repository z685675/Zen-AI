- 崩溃截图显示主进程 `CrBrowserMain`、`EXC_BREAKPOINT (SIGTRAP)`；没有完整调用栈。尚不能确认该次原生崩溃的最终原因。

## 本地已修复的确定问题

1. **输入回显混入答案**：Claude SDK 的 user 帧包含用户输入、附件和底座内部续写提示，原转换器会把普通 user 文本变成助手正文。现在仅处理其中的工具结果，不把输入回显显示为答案；明确的本地命令输出仍可显示。
2. **空响应误判成功**：正文开始/结束、用量和 finish 等控制帧不再被当成任务进展；全空或仅思考但没有正文/工具结果的完成不会保存为正常空答案。空事件不会关闭首次有效输出的超时保护。
3. **异常恢复竞态**：同一运行实例的事件依次处理，替换运行实例后忽略旧实例已排队的事件，避免 error 后紧接的 complete 提前结束恢复中的任务。
4. **503 恢复覆盖不足**：暂时性连接失败在首次输出之前也可进行一次受控恢复，保留当前任务和已有执行记录；已执行工具时提示核验现场，避免盲目重做。SDK 和服务端仍有各自的请求重试，本地会话恢复不是无限循环。
5. **协议转换伪成功**：收到空内容或未正常结束的流，不再向底座发送成功结束标记；SDK 明确标注的错误消息按错误处理，不作为正文。
6. **Excel 空范围膨胀**：不再按 `!ref` 遍历整片矩形。按实际有值/公式的单元格读取，保留原行号、数值、公式、合并范围；相隔很远的列使用单元格地址表达。对过量内容设置提取上限，不能通过兼容解析绕开；自动提取失败会明确告诉助手继续分批读取原文件。
7. **不必要的内存与日志占用**：不再保存仅用于计数的完整 SDK 消息数组；日志不再序列化完整输入/每条 SDK 消息；运行程序 stderr 缓冲有界。

## 新补充的 API 故障证据与链路检查

用户提供的四种错误不能直接当作同一请求的完整时间线：

- 524：连接已建立，但代理等候源站响应超过 120 秒；尚不确定发生在自有网关还是上游的代理。
- 429 `Resource has been exhausted`：上游报告资源或配额耗尽，可能涉及速率、并发或额度，需结合完整响应判别。
- 503 `No available channel ... under group 新渠道不降智 (distributor)`：用户后续确认该分组属于上游。因此这条是上游网关的无可用渠道报错，不是 Zen API 本地分组路由找不到渠道。
- 403 `All available accounts exhausted`：返回方报告账号池无可用账号，不能仅按普通权限不足解释。

本地 Zen API 源码确认：

1. 普通调用按 channel ID 累计连续失败，阈值为 2；需开启全局自动停用和渠道自动停用才会实际停用。SDK 等层的独立 HTTP 重试可能贡献多次计数，不等于用户必须点击两次发送。
2. 普通调用的 `ShouldRecordChannelFailure` 不复用 `ShouldDisableChannel` 的状态码/关键词筛选，还显式允许上游 HTTP 400 计数。因此请求不适用与渠道不可用的区分不足；调整停用状态码也不一定能改变普通调用计数路径。
3. 单 Key 渠道停用会更新整个渠道的模型可用状态，不是只隔离本次失败的模型/接口。
4. 单渠道手动测试直接选定渠道，默认短提示为 `hi`，普通 GPT 测试默认输出上限 16 tokens。成功仅返回测试结果、更新耗时，不调用恢复启用或清除失败计数。
5. GPT 智能助手 Codex 配置使用 Responses 协议；未明确指定端点的 `gpt-6-luna` 面板测试默认构造 Chat Completions 请求。测试成功不能证明 Responses、工具、长输入和真实分组均正常。

这些发现说明临时错误可能被停用策略放大，但尚不能证明本次四个错误均由客户端构造请求引起，也不能证明其与 Mac 原生崩溃同源。后续已在本地修正 API 计数规则（见下节），没有修改生产状态。

继续核实需要对应日志的时间、渠道 ID、请求路径、使用分组、请求 ID、原始错误详情，以及渠道自动停用原因；不要提供 API Key。请求 ID `202610091536541553489948268d9d6EX644TBm` 随上游错误返回，不应未经核对就当成 Zen API 自己的请求 ID。

用户目前无法提供原 Excel、`.ips` 和新的诊断包，不再以提供这些文件为前提阻塞本地确定性修复。但完整 Mac 原生崩溃根因及生产故障时间线仍不能确认。上游 503/403/429 可以继续被 Zen API 记录为所选渠道的失败，不能据此推断 Zen AI 请求使上游模型永久失效。

## 智能助手任务链路补充修复

这些修复不只处理应用退出，还处理任务无法继续、工具未真正执行和错误恢复异常：

1. 通用接口桥接保留工具返回的实际图片。之前截图仅转成图片占位文字；现在将全部并行工具结果放在一起，再附带关联工具调用 ID 的图片消息，供模型查看。
2. 工具参数必须是完整 JSON 对象。截断/非法工具调用不会被标成成功；兼容渠道有工具调用却返回 `stop` 时，修正为 Anthropic 的 `tool_use`，让 SDK 继续工具往返。
3. 去掉转换层额外重试（`maxRetries: 0`），保留底座和网关自身机制以及会话层的一次受控恢复，不宣称全链路只会请求一次。
4. 转换层错误保留上游 HTTP 状态，并区分认证、权限、限流、过载等类别，不全部变成无法识别的通用异常。
5. Codex 必须收到 `turn.completed`，Claude Code 必须收到最终 result 对应的 finish，才能判任务成功。进程/迭代器在工具执行后提前结束，会进入失败恢复，而不是假装任务完成。
6. 普通任务在工具结束后重新等待模型续答时，180 秒无有效进展会尝试一次带执行记录的恢复；恢复失败则明确停止。工具正在执行或等待用户接管时不使用此续答计时器。深度研究仍使用原有独立总时限与接管暂停逻辑。
7. 任务最终失败时同时取消底座，避免界面已结束、后台 SDK 仍持续重试。日志不再序列化整份包含附件的请求。
8. 智能助手附件成功保存到工作区时，不再预先完整解析并注入首条请求；由 SDK 工具按需读取原文件。仅保存失败的文档使用文字兜底，全部文档合计最多 24,000 字符，省略部分明确标记，不冒充完整读取。AI 对话的附件处理不因此取消。

Zen API 本地同步修复：

- 上游 400/413/422 请求错误不触发渠道停用；仍允许按原路由策略尝试其他兼容渠道。
- 普通调用的失败计数统一遵守现有自动停用状态码/关键词设置，以及取消、内容过滤等排除条件。
- 渠道未开启自动停用时，不再积累其自动停用计数。
- 不擅自关闭现有保护。配置中允许停用的 403/429/503/524 仍可能在达到阈值时停用；本补丁不等于屏蔽上游真实故障。
- 没有改变生产渠道状态，也没有把短请求探活成功当作全协议恢复的证明。

新增测试使用真实 Anthropic SDK / AI SDK 编解码，模拟 OpenAI 通用接口回复和工具结果，覆盖 GPT/Gemini/Claude/Grok 名称路由、工具调用→图片与结果回传→正文、403/429/503/524 状态保留、没有转换层隐藏重试、截断工具参数。另有 Codex EOF/失败事件、续答停滞、终止后取消底座和附件文字兜底上限测试。它们不是生产上游实测，也不替代 ARM Mac 安装包验收。

## 66 → 70 回归对照

已核对本地真实标签 `v1.1.66` 与 `v1.1.70`。以下大部分变动集中在 `2ff3eca0`（`feat: improve assistant context and multimodal workflows`），不能把该提交全部内容都认定为故障原因。

| 环节 | 66 版 | 70 版 | 本轮判断 |
| --- | --- | --- | --- |
| Excel 结构化解析 | 基于工作表 XML 中的实际内容 | 新增 XLSX 库解析，按 `!ref` 展开完整矩形 | 明确新增高风险路径，已修稀疏提取并构造全表范围的小文件回归用例；是否为用户本次原生崩溃原因待 `.ips`/原文件确认 |
| 智能助手首条附件输入 | 没有新增的 UI 附件完整预解析链路 | 保存附件后还完整提取文本并注入请求 | 新增阻塞/请求膨胀路径；已改为落盘后由底座按需读 |
| 断线恢复 | 没有本次新增的 stream recovery 流程 | 新增同底座重建及恢复事件 | 新增事件并发和旧 finish 干扰恢复的风险，已串行事件并过滤旧实例 |
| Claude Agent SDK | 0.2.81 | 0.3.273 | 跨版本升级且涉及原生可执行文件，须重点验收；不能仅凭版本变化认定 SDK 自身有 bug |
| Codex SDK | 0.142.5 | 0.154.0 | 同期升级，需覆盖 Responses/工具/恢复，不只测 Chat Completions |
| Anthropic API SDK / MCP SDK | ^0.41.0 / 1.27.1 | ^0.126.0 / 1.30.0 | 协议及工具依赖同时升级，需要真实编解码往返测试 |
| 默认底座选择 | 模型倾向+能力评分+会话连续性 | 显式 GPT 优先 Codex，其他优先 Claude Code | 对 GPT 两版原本均倾向 Codex，不应简单归因为新版本把所有 GPT 改了底座 |
| 原生运行程序打包/启动 | 旧 SDK 启动方式 | 70 另有 `cca35daf` 修复原生二进制打包与 spawn | 主要解释此前 Mac 立即启动失败，不足以解释所有复杂任务/上游错误 |

特别区分：SDK user 文本误作答案、桥接丢工具图片、流 EOF 误判完成等缺陷在 66 的相关代码中已存在。它们是需要修复的既有风险，不应包装成已经证实的 66→70 新回归。新版 SDK 行为或复杂工作流可能让这些风险更易暴露，但仍需实际调用记录验证。

## 无需用户原文件的最小 Mac 验收

在包含修复的新包中，用同一 Provider、同一模型、同一会话顺序发送以下三条。测试 GPT 的 Codex 路径后，再在新会话选择 Gemini/Claude/Grok 中一个可用模型重复，验证 Claude Code 通用接口路径。测试不需要用户提供私有文件，但不能复现原 Excel 的特殊结构。

1. `请在工作区创建一个真正的 Excel 文件“小表测试.xlsx”。第一行是“地区、销售额”，下面三行分别是“华东、1200”“华南、800”“华北、1000”。请实际生成文件并给我打开入口，不要只发制作方法。`
2. `请实际读取刚才生成的“小表测试.xlsx”，告诉我销售额合计是多少，并列出你读到的三行数据。`
3. `请把华南的销售额改成900，另存为“小表测试-修改后.xlsx”，保留原文件。保存后重新读取新文件，告诉我新的合计。`

通过条件：有实际工具执行和可打开的 XLSX；原表合计 3000，新表合计 3100；工具执行后能继续给出正文；不显示底座内部英文续写提示；不出现假成功、长时间无反馈或应用退出。上游明确报告账号/额度不足时可以结束为清晰故障，不能以假成功掩盖。
